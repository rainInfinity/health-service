# health-data-model Specification

## Purpose

为账号健康资料、渠道与模型目录、推理任务、原始文件和结果指标提供一致的持久化契约，使后续用例能依赖稳定的归属关系、空值含义与数据库完整性约束，而不把建表等同于业务流程已经实现。

## Requirements

### Requirement: 账号与健康资料的持久化关系
系统 MUST 为账号保留唯一的用户名、可为空且在逻辑删除后仍唯一的手机号、密码哈希、账号可用及管理权限标记；一个账号至多关联一份以账号 ID 为主键的健康资料。

#### Scenario: 已停用账号的手机号不释放
- **WHEN** 某账号已有手机号，并被标记为不可用且记录逻辑删除时间，随后尝试为另一账号保存相同手机号
- **THEN** 数据库拒绝重复手机号，同时保留原账号与其关联记录

#### Scenario: 未绑定手机号的账号
- **WHEN** 创建多个尚未绑定手机号的账号
- **THEN** 这些账号可以将手机号保持为 `NULL`，各自拥有独立的账号 ID

#### Scenario: 健康资料的共享主键
- **WHEN** 为一个账号保存健康资料
- **THEN** 资料的主键等于该账号 ID，且同一账号不能再保存第二份资料

### Requirement: 健康资料区分未知与实测值
系统 MUST 支持姓名、出生日期、身高、体重、病史文字和结构化病史逐步填写；未知测量值使用 `NULL`，性别 `0` 表示未知，已知结构化病史标记缺失时不得默认为 `false`。已定义病史标记 MUST 在内部数据和持久化 JSON 中使用 `is_diabetic`、`is_hypertensive`，不得将 HTTP 的 `isDiabetic`、`isHypertensive` 别名作为这些字段的存储键。

#### Scenario: 部分资料未填写
- **WHEN** 账号资料未提供姓名、出生日期、身高、体重或结构化病史标记
- **THEN** 可选字段保持 `NULL` 或缺少对应 JSON 键，性别可为 `0`，系统不将未知身高体重写成 `0`

#### Scenario: 无效资料值
- **WHEN** 写入不在 `0`、`1`、`2` 范围内的性别，或非空且不大于零的身高／体重
- **THEN** 数据库拒绝该值

#### Scenario: 已定义病史标记以内部键持久化
- **WHEN** 业务资料更新保存糖尿病为 `true`、高血压为 `false`
- **THEN** 持久化病史为 `is_diabetic: true`、`is_hypertensive: false`，这两个已定义字段不同时生成对应驼峰存储键

#### Scenario: 未提供标记不制造默认值
- **WHEN** 业务资料更新只保存糖尿病标记且此前没有高血压标记
- **THEN** 持久化病史包含 `is_diabetic`，不产生 `is_hypertensive`，不会把缺失标记写成 `null` 或 `false`

### Requirement: 渠道与模型版本目录
系统 MUST 分别持久化具有唯一 label 的渠道、具有唯一 code 的模型及其版本；同一模型内版本号唯一，同一渠道与模型的配置至多有一个当前版本指针，不同渠道可引用同一版本。

#### Scenario: 渠道独立选择版本
- **WHEN** 两个渠道各自保存同一模型的当前版本选择
- **THEN** 各渠道分别只有一行该模型的配置，两个指针可以指向同一版本或不同版本

#### Scenario: 重复目录标识
- **WHEN** 写入重复的渠道 label、模型 code、同模型版本号或同一渠道与模型的第二条配置
- **THEN** 数据库拒绝该重复关系

### Requirement: 模型制品与可投影指标目录
系统 MUST 为模型版本保存算法标识、参数和发布时间，并支持一版本多制品及一版本多可投影指标；制品的同版本逻辑名、存储键，指标 code 及版本与指标的关联必须遵守各自的唯一性约束。

#### Scenario: 登记模型制品
- **WHEN** 为某版本登记具有正数大小的制品与唯一存储键
- **THEN** 该制品与版本关联；同版本同名、重复存储键或大小不大于零的记录被数据库拒绝

#### Scenario: 指标属于多个模型版本
- **WHEN** 多个版本引用同一个数值或布尔指标定义
- **THEN** 每个版本可独立记录一次该关联，但同版本不可重复关联同一指标

### Requirement: 推理任务的归属与版本记录
系统 MUST 将任务关联到账号、渠道及确定的模型版本，并保留状态、健康资料快照、提交／开始／结束时间以及结果或失败诊断字段；新任务默认为 `DRAFT`，草稿允许没有快照与业务时间。

#### Scenario: 保存任务草稿
- **WHEN** 为现有账号、渠道和模型版本创建任务，尚未填写快照或提交时间
- **THEN** 任务以 `DRAFT` 状态持久化，并保留账号与版本引用

#### Scenario: 引用不存在的归属
- **WHEN** 任务引用不存在的账号、渠道或模型版本
- **THEN** 数据库拒绝该引用

### Requirement: 任务终态与结果字段一致
系统 MUST 只允许 `DRAFT`、`SUBMITTED`、`RUNNING`、`SUCCEEDED`、`FAILED` 状态；只有 `SUCCEEDED` 任务有非空的完整结果，`FAILED` 任务必须记录完成时间与失败代码，非失败任务不得保留失败字段。

#### Scenario: 保存成功结果
- **WHEN** 任务以 `SUCCEEDED` 状态保存完整结果和完成时间，且不含失败字段
- **THEN** 数据库接受该记录；成功任务缺少结果时拒绝保存

#### Scenario: 失败或未结束任务的字段冲突
- **WHEN** 保存缺少失败代码的 `FAILED` 任务，或为未成功任务写入结果，或为非失败任务写入失败字段
- **THEN** 数据库拒绝与状态不一致的记录

### Requirement: 原始文件的选中记录
系统 MUST 为任务保存每次上传的独立文件记录；存储键全局唯一、文件大小大于零，同一任务和逻辑名至多有一条选中记录，未选中的历史记录允许共存。

#### Scenario: 保留同名历史记录
- **WHEN** 一个任务已有某逻辑名的未选中文件，随后保存同名的新选中文件
- **THEN** 两条记录都保留，只有后一条被标记为选中

#### Scenario: 两条同名文件同时选中
- **WHEN** 同一任务同一逻辑名的两条文件记录均标记为选中
- **THEN** 数据库拒绝第二条选中记录

### Requirement: 任务指标值的唯一投影
系统 MUST 允许任务按指标记录至多一个投影值；一个投影值必须且只能占用数值列或布尔列之一，不存在的指标不以零或 `false` 填充。

#### Scenario: 数值和布尔投影
- **WHEN** 为同一任务保存不同指标的数值与布尔投影
- **THEN** 各投影分别记录对应类型的值，另一类型的列保持 `NULL`

#### Scenario: 缺值或重复投影
- **WHEN** 同一投影的两个值列均为空、均非空，或同一任务对同一指标重复写入
- **THEN** 数据库拒绝该记录

### Requirement: 业务实体的审计字段
系统 MUST 为十二种业务实体保留非空的创建与修改时间，以及可为空的创建／修改操作人稳定标识；操作人标识不依赖可变用户名或当前请求上下文。

#### Scenario: 未提供操作人上下文
- **WHEN** 由无操作人上下文的迁移或后台进程创建业务记录
- **THEN** 时间字段仍有值，操作人字段可以为 `NULL`

#### Scenario: 提供稳定操作人标识
- **WHEN** 写入方明确提供 `user:<id>` 或 `system:<component>` 形式的操作人标识
- **THEN** 记录保留该标识快照，而不是保存与用户表的外键
