# Design

## Context

动机与范围见 [proposal.md](proposal.md)，行为契约见 [血氧增量规格](specs/inference-algorithms/spec.md)。当前 `OfflinePipeline` 已提供输入、预处理、质量、推理、后处理和输出阶段；HR/BR v1 无制品。`infrastructure/inference_adapter.py` 的 `_VersionRuntime` 仅缓存定义、参数和制品键，未缓存模型会话；`AlgorithmDefinition` 目前持有静态 `runner`。

旧实现位于 `/Users/junsi/project/nxhe-backend/src/models/services/spo2/`，共享源码来自该项目 `libs/pyPPG/`。旧实例保存任务输出路径，按输入路径和文件名推导输出位置；不能直接作为共享运行时。旧特征链依赖 sklearn StandardScaler、SciPy、DotMap、本地 pyPPG 和 ONNX Runtime。

提供的血氧测试制品位于 `var/old-assets/`：完整清单为可安全读取的 Unicode NPY，含 363 个唯一名称；稳定清单的 pickle 静态解析为 22 个唯一名称，全部在完整清单中，其中 9 个名称包含 `_ppg_`。此数量描述当前测试制品，不是所有未来模型的固定契约。

参考文件 `var/old-assets/sample/20261101_134952-5-2-bp_vlatest-ppg.csv` 已通过现有 PPG 读取器：929 行 YUV，采样率 30 Hz，时间跨度约 30.93 秒，默认规则生成 7 个窗口。未执行血氧 ONNX、未验证该样本质量通过，也无已确认旧版预测。当前环境缺少 ONNX Runtime、ONNX 和 DotMap。

## Goals / Non-Goals

**Goals:**

- 把共享第三方库、算法固定规则、模型版本资源和任务状态分成明确边界，保留可核验的数值基线。
- 正式运行只读取不可执行的特征清单；Web 注册与启动不导入推理重依赖。
- 用真实测试制品证明逐层计算与受保护任务链路，而不是用固定输出替代模型执行。

**Non-Goals:**

- 不以复制旧类的方式保留旧路径协议、ORM 或可变任务容器。
- 不把测试模型、样本或管理上传操作加入生产启动、迁移和默认种子。
- 不保证跨依赖环境逐位相同，不把限幅范围解释为医学证据，不隐式修正训练相关特征。

## Decisions

### 1. pyPPG 是包内共享第三方源码，不是血氧私有工具

完整源码放在 `packages/health-inference/src/health_inference/libs/pyPPG/`，通过 `health_inference.libs.pyPPG` 引用；调整内部绝对导入，不保留顶层 `libs` 别名。保留第三方原有注释、署名和许可，不做风格重写或算法重构。外部依赖兼容修改限定在必要位置，并逐项记录原因和对照结果；不主动导入示例、验证、GUI 或数据交互模块。

在 `docs/development/third-party/pyppg.md` 记录来源目录、可确认的上游信息、原始逐文件 SHA-256 与迁入基线、适配清单、许可核实结果和验证环境。目前上游版本未知，不能根据同名包猜版本；后续共享库变动必须验证所有已使用算法。许可信息缺失不能视为无约束：实施时沿源仓库来源线索核实上游许可，未解决前不得将该第三方库作为可分发生产制品交付。

选择 vendored 源码而非重新安装 pyPPG：旧训练兼容性依赖实际代码，不依赖包名。共享位置避免每个算法复制，但绝不允许新算法顺带改写旧算法的计算解释。

### 2. 血氧实现按职责拆分，不依赖 HR/BR 修订内部模块

在 `algorithms/ppg_active_offline_spo2_v1/` 放置算法专属模块；跨算法共用的 PPG CSV 解析器位于 `health_inference/utils/ppg_input.py`：

| 模块 | 职责 |
|---|---|
| `algorithm.py` | 定义标识、输入输出契约和版本资源工厂，装配流水线 |
| `health_inference/utils/ppg_input.py` | 共享单块 RGB/YUV CSV 解析、通道和时间轴校验，并拒绝多块输入 |
| `load_input.py` | 在共享解析后校验算法特有边界，如最小窗口长度和可执行采样率 |
| `preprocessing.py` | 旧颜色转换、负红波形、带通和 Z-score，保留特征所需颜色数据 |
| `quality.py` | 质量计算与固定阈值门禁 |
| `features.py` | AC/DC、九通道、窗口基础特征和 pyPPG 特征 |
| `inference.py` | 特征排序筛选、任务内标准化归一化、ONNX 输入和原始预测 |
| `postprocessing.py` | 预测结构与有限性校验、最大值和限幅 |
| `build_output.py` | 最终载荷、指标、波形文件和结果校验 |
| `resources.py` | JSON 清单、ONNX 资源加载与配套校验 |

使用 `OfflinePipeline` 的现有阶段顺序。预处理只准备颜色数据及质量波形；通过质检后，推理阶段调用特征模块并运行模型，避免低质量任务消耗昂贵特征计算。只有成功输出阶段写文件。

不直接 import HR/BR v1 私有读取器或类型。单块 RGB/YUV CSV 的共同解析放在 `health_inference/utils/ppg_input.py`，由 HR/BR v1 与 SPO2 v1 共用；各自 `load_input.py` 只添加算法特有边界。HR/BR 原有输入边界、数值结果和错误原因必须回归不变；不得通过共享模块顺带统一颜色量级或增加呼吸波。

### 3. 固定 v1 参数和训练相关计算行为

第一版采用已观察旧默认配置：窗口 450、步长 75、`apply_diff=false`，模型参数只允许空映射；这是本提案选择的默认，不声称已确认旧生产部署配置。以后需要支持其他解释或新增可调参数时走显式契约修订，不接受透传任意字典。

RGB 特征保留原始量级；YUV 按旧 BT.709 转换并除以 255，不为外观一致改变旧训练输入。九通道按 `r,g,b,r_ac,r_dc,g_ac,g_dc,b_ac,b_dc` 排列；保留旧 AC/DC、翻转、内部 125 Hz 重采样、生物标志物名称及统计解释。

按完整清单构建矩阵，保留旧规则下未产生特征填零的解释，再按稳定清单顺序筛选。填零仅适用于明确的缺省特征，不用于掩盖依赖缺失、程序异常或已有特征的 NaN。清单、预处理、特征矩阵和模型输入均须进行有限性及形状检查，程序产生的无效特征不冒充输入错误或质量拒绝。

保留本任务窗口内的 StandardScaler，再执行 `(X_std-min)/(max-min+1e-8)`，最后转 float32。为兼容先沿用 sklearn 的实现并锁定依赖，不趁迁移改写成看似等价公式。一个窗口或常量列归一化为零，不静默增加窗口或改变最小输入量。7 窗口参考样本不替代单窗口边界验证。

旧特征代码将任意异常降为基础特征。此次明确区分：短信号、近常量信号或特征点确实为空等可明确识别的预期退化保留基础特征路径；导入失败、API 不兼容和未知异常直接受控执行失败，不打印原始异常、不继续补零。pyPPG 内部原有算法分支保持基线；如果参考输入触发未预期异常，解决真实兼容原因，不以扩大捕获范围凑成功。

### 4. 三件套清单转 JSON，版本资源不执行 pickle

正式逻辑名固定为 `spo2`、`feature_names`、`stable_features`；前者 ONNX，后两者为 UTF-8 JSON 字符串列表。模型输入特征数由稳定清单决定，不硬编码测试制品的 22。

测试准备阶段用 `np.load(..., allow_pickle=False)` 读取现有 Unicode NPY。对已检查为简单字符串列表的稳定清单，可用不允许加载全局对象的受限转换读取方式或静态解析转换；正式资源加载只支持 JSON，不保留旧 pickle 兼容路径。转换严格保留原顺序并与旧清单核对。原始文件保持不变，转换结果也只服务测试上传。

加载时检查非空清单、非空字符串、名称唯一、稳定特征属于完整清单，构建一次索引；模型要求一个 float32 二维输入，特征宽度须匹配稳定特征数，批维须支持窗口批量，输出为每窗口一个数。预测接受 `[N]` 或 `[N,1]`，统一为一维保留原顺序，其他形状拒绝。实际模型是否符合这些条件由提供的 ONNX 检查和运行证明；不通过时报告真实制品不兼容，不补列、转置猜测或重训。

无需扩张现有发布事务为重模型加载：发布继续校验逻辑集合、文件存在、参数和指标；内容兼容检查发生于版本资源首次构建。测试版本正式发布前，通过独立资源加载 smoke 验证三件套。

### 5. 统一版本资源工厂，替换静态 runner 约定

在纯计算契约中定义版本资源输入（只含固定参数和已解析制品路径）与受控资源工厂；创建的版本运行时持有流水线和只读可复用资源，并负责执行时统一契约校验。用这一工厂替换 `AlgorithmDefinition` 当前静态 `runner` 字段，所有正式算法、直接调用及测试注册方同步迁移，不保留旧字段或双执行路径。HR/BR 工厂返回无权重流水线，计算行为不变。

服务端 `_version_runtime(version_id)` 解析不可变配置和制品路径后构建一次绑定运行时，缓存键仍是固定发布版本主键，不能是算法 key、模型名称或渠道当前选择。缓存对象只保存定义、固定参数及会话和特征索引，不保存 `InferenceInput` 或任务数组。单次调用仍须检查任务必需文件、快照、固定参数和完整结果，资源缓存不是绕过契约的捷径。

缓存有效期内依赖已发布制品不可变约束，旧版本资源保持可用；测试版本 A/B 交错执行覆盖配置污染风险。消费者停止新领取并排空后清缓存，释放 ONNX 引用，不删除制品。沿用现有消费者执行调度，不为此引入新的并发线程池；若未来允许并发首次构建，必须保证同版本资源安全发布。

### 6. 质量与后处理保留已确认规则，先校验后限幅

质量分数沿用 NeuroKit2 `ppg_quality` 均值乘 100，采样率按旧链传 `int(fs)`，阈值 70，不舍入；低分报告实际比较值，非法评分或意外异常仍为执行失败。

模型输出必须非空、数量等于窗口数且全部有限；任一无效即 `RESULT.INVALID_OUTPUT`，不筛掉坏窗口。合法输出取最大值，再执行 `[90,100]` 限幅，不改均值、不四舍五入。两项规则均经用户确认。单窗口零特征、取最大值和下限 90 具有已知局限，但此次不自行改变。

完整载荷建议使用 `spo2`、`quality`、`window_predictions`、`window_starts` 和正式身份标志；最终字段以既有任务结果载荷约定保持一致。投影为同一最终 `spo2`，单位 `percent`。处理后 CSV 使用 `timestampFrame,ppg`，保留原毫秒时间轴和质检所用处理后波形，写入本次 `output_dir`，只通过逻辑名 `processed_ppg` 返回。失败不发布任何成功波形引用。

### 7. 测试制品只进入显式测试操作，不进入产品初始化

用户提供的 `var/old-assets/` 与其中样本均是测试资料。只处理血氧 ONNX、两份清单和 `sample/20261101_134952-5-2-bp_vlatest-ppg.csv`；不使用同目录 ACC、frame，不根据文件名 `bp_vlatest` 选择算法，也不处理其他模型。

验证在持久测试数据库、测试存储根和测试 Redis 命名空间中运行，避免污染开发或生产模型选择。通过既有管理 API 创建明确命名的测试模型/版本、上传转换后的三件套、配置指标、发布和选择测试渠道，再由普通测试用户提交 PPG，通过实际消费者完成任务并下载文件。使用既有测试账号，不将密码或令牌写入日志、提案或可提交脚本。

每次 smoke 使用明确测试标识，遇到已存在配置应核对或新建测试版本，不覆盖已发布版本或任意重指已有渠道。文档给出显式操作步骤，不增加自动初始化命令、生产种子或启动副作用。测试文件保持本地，不复制真实样本到公开示例或永久测试夹具。

### 8. 验证先逐层对照，再证明任务链路

在同一已锁定环境对旧代码计算函数和迁移链逐层比较；不运行旧入口的路径写入和模型加载副作用。记录颜色转换、九通道、窗口位置、特征名与矩阵、稳定索引、标准化、归一化、原始窗口预测及最终结果。首次对照应报告最大绝对/相对误差和预先选择的数值容差（float64 特征默认 `rtol=1e-6, atol=1e-8`，float32 模型输入和预测默认 `rtol=1e-5, atol=1e-6`）；不得只因最终限幅都为 100 就认定一致。超差定位原因，不事后放宽容差凑通过。

若参考样本明确质量不通过，端到端诚实验证拒绝路径；另外以确定性合成且实际通过质量的 PPG 验证真实 ONNX 成功链，不关闭质量门禁。旧基线若因环境异常无法运行，先解决兼容问题或明确阻塞，不虚构旧版参考值。

永久测试只覆盖消费者可见风险：输入边界、门禁、有限性和窗口对应、最大值与限幅、单窗口解释、清单顺序、版本隔离、输出一致和越权下载；使用合成数据与隔离资源，不能要求共享仓库外旧目录或本地私有制品。真实本地样本用于一次性对照和端到端 smoke，不成为默认测试套件必需条件。

## Risks / Trade-offs

- 下限 90 隐藏更低预测 → 保留已确认兼容规则，在算法文档和测试用途说明中明确，不宣传为低血氧诊断。
- 单窗口全部零输入，原始 RGB 与 YUV 特征量级不同 → 保留训练相关行为并逐层对照，不借迁移修复；改变必须用新修订。
- 旧广泛异常捕获曾掩盖依赖故障 → 仅保留明确退化条件，未知异常失败；兼容排查不能通过补零绕过。
- pyPPG 上游版本与许可尚未确认 → 用源码指纹准确固定现有基线，追查来源和许可；未核实不宣称可分发。
- Python 与 pandas 等环境不同可能改变特征 → 锁定实际依赖并记录验证环境，实测对照，不以目录复制代替兼容性证据。
- 模型输入输出形状尚未读取 → 安装测试推理依赖后首先检查并执行提供的三件套；不承诺未观察到的输出值。
- 版本缓存保存模型资源增加内存 → 仅缓存可复用资源，不缓存任务矩阵，排空退出释放；本次不扩展为通用 LRU 或动态卸载框架。
- 本地参考 PPG 可能未通过质检 → 不篡改输入或绕过门禁，以实际拒绝结果报告，并另用确定性可用输入完成成功 smoke。

## Migration Plan

1. 核实并固定 pyPPG 源码来源与依赖，完成必要导入适配和直接特征验证。
2. 引入统一版本资源工厂并迁移 HR/BR、适配器和全部测试调用方，先保证旧行为不变。
3. 加入血氧固定实现与受控注册，更新计算依赖和文档；不自动发布任何模型。
4. 在隔离测试环境转换并上传给定制品，完成逐层对照和真实任务/下载 smoke，记录观测结果。
5. 生产使用需要另行提供和审批生产制品、显式创建发布版本及渠道选择；本次不执行。无需数据库 schema 迁移。
6. 回退通过既有渠道选择切回已发布可用版本；已提交血氧任务仍保留原修订和资源执行能力，未排空前不能删除算法代码或制品。源码回退只在相关任务排空后进行，不重解释历史任务。
