# Design

## Context

动机见 `proposal.md` 的 Why；对外行为以本变更四份差量规格为准。

当前实现的约束：

- `Task.model_version` 是单外键，`ModelVersion.algorithm_key` 是单标识；`application/tasks.py` 继续负责草稿、一次上传、一次冻结资料与提交。
- `AlgorithmDefinition.create_runtime()` 绑定不可变参数与制品，`AlgorithmRuntime.run()` 校验并执行单算法完整契约。四个成员已提供真实计算实现，无需重写信号处理。
- `infrastructure/inference_adapter.py::_version_runtime()` 目前先逐个解析且确认所有制品存在，再创建运行时；任一失败会在场景执行前终止整个任务。资源工厂若同时急切初始化全部成员，也有同样问题。
- `application/execution.py::_safe_failure_fields()` 持有现有安全失败码、受控输入原因和类型化质量拒绝的白名单映射，计算包不能反向导入 service。
- 计算载荷禁止顶层 `output_files`，由服务验证路径后追加受保护引用；`result_validator` 在计算结束和保存前都会被使用。
- 文件验证已允许执行目录后代文件，发布函数将整个令牌目录链接为正式目录。因此子目录可复用现有能力，但只从字典移除失败文件并不能避免其残留目录被一起发布。
- `Task.result_payload`、指标和终态原子保存；数据库规定只有 SUCCEEDED 才有完整结果。消费者提供整体硬时限和失租恢复，不具备成员级持久化检查点。

## Goals / Non-Goals

**Goals:**

- 在原有单 Task 执行链内增加两个可发布的真实场景执行器，场景调用原成员运行时，成员自己的门禁和结果仍保持原子性。
- 成员资源加载失败、输入拒绝、质量拒绝和执行/结果异常均可隔离；所有失败信息必须在进入权威结果前完成安全化。
- 固定场景结果协议、版本归属、指标来源和文件命名，并让原独立算法行为不变。
- 发布和下载只接受成功成员的本次产物，不能借场景成功将失败成员文件发布。

**Non-Goals:**

- 不增加 Measurement 父表、子 Task、任意算法列表参数、通用 DAG 或独立成员消息。
- 不同时保留三套独立模型版本指针；场景发布版本拥有自身制品集合，成员实现修订固定在代码中。
- 不合并预处理或质量评分，不修复现有数值链，不新增采集门槛、插值或时钟对齐。
- 不实现中间进度返回、成员重试、成员硬超时、并行推理或跨进程共享资源。

## Decisions

### 1. 将场景注册为新的算法定义，而不是新的业务任务类型

新增实现目录：

- `health_inference/algorithms/ppg_active_offline_all_v1/`
- `health_inference/algorithms/ppg_acc_active_offline_all_v1/`

分别注册精确 key `ppg.active.offline.all.v1` 和 `ppg_acc.active.offline.all.v1`。算法注册与公共包导出沿用当前约定，Web 导入不得加载模型及信号处理重依赖。

新增按场景职责命名的纯计算编排模块，保存两个固定声明并实现公共的成员执行和汇总规则；不建立可配置流程引擎。声明明确成员顺序、标识、所属指标和输出命名范围，成员引用既有的完整算法定义，禁止通过字符串包含 `all`、数据库类路径、注册表枚举或 latest 推导执行范围。

| 场景名称 | 固定顺序与成员 | 上传输入 | 场景版本制品 |
|---|---|---|---|
| 统一PPG场景 | hr_br → spo2 → diabetes | ppg | spo2、feature_names、stable_features、diabetes |
| 统一PPG+ACC场景 | bp | ppg、acc | sbp、dbp、normalize |

场景的必需资料字段为空、固定参数为空、is_example 为 false；输入/制品后缀和指标契约使用各成员既有声明的并集，不重新抄写另一份单位与格式规则。对当前固定集合，制品名和指标代码没有冲突；声明校验必须拒绝冲突，不能后项覆盖前项。

Model.name 是数据库配置，不属于 AlgorithmDefinition。文档用用户确定的两个名称指导管理配置；Model.code 可沿用既有命名约定采用去掉实现修订的场景 key，但客户端必须使用目录实际返回的值。

**取舍：** 不采用父测量＋子任务方案，因为已确定需求是新增算法调用既有算法。单场景版本即可冻结资源，不必改变数据库和 Redis 消息语义。

### 2. 一个场景发布版本直接固定全部成员制品

场景版本绑定上述并集制品，发布仍要求完整集合、允许后缀及物理文件存在，不为“部分成功”放宽发布校验。成员工厂仅获得该成员的制品子集与空参数；成员使用同一任务的文件引用、冻结资料和元数据，但各次调用创建独立输入对象，不能把任务数据写入复用运行时。

成员实现修订由 all.v1 声明固定，场景制品由 Task.model_version 固定。因此独立 HR/BR、血氧或糖尿病模型切换发布版本不会改变场景；更新场景制品需创建新的场景发布版本，改变成员集合或计算解释需新增场景实现修订。

**取舍：** 不从场景参数保存其他 ModelVersion ID，也不在每个成员执行时查询渠道当前版本。前者引入跨版本发布和生命周期依赖，后者无法保证一次采集的固定解释。

### 3. 将成员资源初始化纳入成员失败边界

场景工厂只绑定固定资源引用与成员声明，不在创建外层运行时时一次加载全部模型。每个成员首次使用时才调用其 `create_runtime()`；成功创建的运行时可在该场景发布版本缓存中复用，失败初始化不保存为永久失败状态。某任务的成员初始化失败不触发本次重试；后续新任务正常尝试资源准备，不复用上次的任务失败信息。

适配器保留对声明集合、场景版本、参数和路径安全的全局检查。对于两个显式注册的场景，物理制品的存在性和文件类型检查延迟到相应成员实际初始化，避免一个缺失成员文件提前阻止所有成员。

实现上在本地存储层提供有明确调用范围的候选文件引用解析：仍校验登记键、根目录、路径段和现有符号链接，允许最终文件缺失但不允许越界；默认 `resolve_file` 和所有上传、发布、下载及普通算法调用继续要求实际文件存在。可以为既有解析方法增加默认保持原行为的显式选项，或在同一存储模块增加职责明确的方法，不能由适配器直接拼接未经校验的路径。场景识别复用固定声明，不以任意客户端字段开启延迟检查。

制品根目录不可用、登记键越界或场景版本结构不完整是场景准备错误；某成员已登记制品缺失、模型不兼容或内容损坏是该成员错误。已缓存且成功加载的版本资源无需为每次任务重新读取模型文件，继续遵循现有资源复用语义。

**取舍：** 不把所有资源错误都提升为场景失败，也不改变普通算法的急切检查。延迟存在性检查是成员隔离所必需，不是放宽目录安全或发布完整性。

### 4. 逐成员顺序调用并在边界内安全捕获

PPG 按 hr_br、spo2、diabetes 顺序执行；PPG ACC 执行 bp。每次调用都使用成员自己的 `AlgorithmRuntime.run()`，不调用被绕过校验的裸预测函数，也不重新实现成员阶段顺序。

成员调用边界包括资源工厂、输入校验、计算、原结果校验及其文件存在性/所属成员目录校验。普通受控错误转换为对应安全成员失败，未预期 `Exception` 转换为通用执行失败。失败后继续下一成员；不捕获 BaseException，不屏蔽进程终止、硬超时或场景自身最终校验错误。

原始任务文件无法在服务准备阶段读取时仍是顶层任务失败。文件可读取但 CSV 内容或采样条件不满足某成员时，由该成员按原契约失败；不得提前使用三个算法的最大长度门槛拒绝全部成员。前端采集建议可以介绍当前共同显式下限 `fs > 8` 且 `N >= max(450, ceil(15*fs))`，但不能承诺满足下限就成功。

**取舍：** 不在本次增加线程或子进程并行。所有成员共用一次 Task 硬时限；资源/数值隔离先于计算去重和吞吐优化。

### 5. 安全失败映射只有一份无框架依赖实现

将 `application/execution.py` 当前纯错误分类、输入原因映射、质量白名单校验和固定安全文案下沉到计算包内职责明确的共享模块，独立任务失败记录与场景成员共同调用。保留当前独立任务失败码和文案，不建立兼容转发别名；更新所有调用方和相关测试，变更公共符号前先用语言服务核对引用。

共享结果只包含安全失败码、固定摘要和可空类型化质量拒绝。服务继续按现有内部 `failure_detail` 结构持久化顶层拒绝，场景则显式构造六字段成员对象；不将内部 failure_detail 原样塞进成功载荷，也不把 traceback、safe_message、自定义附加属性或异常正文当作公开信息。

质量拒绝必须验证类型、错误码、reason、details 与有限数值；伪造、缺失及损坏信息仍按原规则降级为通用执行失败。成员结果校验也要拒绝不匹配的失败代码/摘要及额外公开字段，不仅依赖首次捕获时清洗。

**取舍：** 不在计算包导入 Django service，不复制第二份安全文案表，也不在前端或查询时才尝试从任意异常正文做脱敏。

### 6. 场景载荷与成员载荷分层，任务状态不扩展

计算包场景 `InferenceOutput.payload` 恰好包含 outcome 与 results；公共 HTTP 字段结构在计算契约中显式定义，不能用 ORM 或 HTTP Schema 替代纯计算对象。

| 层级 | 内容与约束 |
|---|---|
| 任务 status | 原五种状态不变；SUCCEEDED 表示编排和汇总完成 |
| result.outcome | ALL_SUCCEEDED、PARTIALLY_SUCCEEDED、ALL_FAILED，严格由成员终态推导 |
| result.results | 固定成员名映射；不得缺项、增加陌生成员或返回处理中状态 |
| 成员 algorithmKey/status | 固定完整修订标识；status 为 SUCCEEDED 或 FAILED |
| 成员 result | 成功时保留原计算 payload，包括独立 quality 和窗口明细；失败时为 null |
| 成员 failureCode/failureMessage/qualityFailure | 成功时均为 null；失败时只含安全字段及合法可空质量拒绝 |
| result.output_files | 服务验证后统一追加的不透明文件引用映射；无成功文件时保持缺席 |

成员 result 不包含 output_files；成功成员的文件只进入场景顶层统一映射，避免双重路径解释。现有服务禁止计算 payload 自带 output_files 的约束不变。

正常汇总即使 ALL_FAILED 也保存为 Task SUCCEEDED，result 非空、指标为空、顶层 failureCode/failureMessage/qualityFailure 为空。只有原始文件读取、场景编排/存储、整体超时或最终汇总契约错误才进入任务 FAILED/result=null。HTTP 查询成功仍是 200/OK，与业务测量结局无关。

场景结果校验从成员的 result、所属指标与去前缀文件映射重建成员 `InferenceOutput`，调用成员原结果校验器，并校验六字段、标识、结局、失败字段以及全场景指标和文件集合的精确一致性。运行过程中发现成员输出无效，可将该成员转为失败后继续；已经返回的最终场景结果若在服务落库前被发现损坏，则按任务级 RESULT.INVALID_OUTPUT 拒绝，不能在持久化层悄悄改写成员结果。

**取舍：** 不新增 PARTIALLY_SUCCEEDED 数据库任务状态。该值只属于场景结果 outcome，因此复用数据库一致性约束、终态处理和历史查询。

### 7. 只合并成功成员指标，并隔离物理文件与逻辑名

成功成员的 metrics 使用原代码和值合并；失败成员贡献空指标，不补零或 false。场景版本选择哪些指标仍由现有发布配置控制，服务只投影成功成员实际返回且版本选中的项。risk_level 不新增指标定义。

物理输出目录为本次 `output_dir/<成员名>/`，成员继续写自己的原文件名及 CSV 表头。输出逻辑名为 `<成员名>_<原逻辑名>`：

- PPG：hr_br_processed_ppg、hr_br_processed_rsp、spo2_processed_ppg、diabetes_processed_ppg。
- PPG ACC：bp_processed_ppg、bp_processed_scg。

成员返回文件需在其固定子目录中存在且为普通文件，不能借其他成员、其他任务或其他令牌的文件充当成功输出。服务仍执行根目录与任务/令牌级二次校验。

成员失败时只清理本次调用新建的固定子目录，不按算法返回路径递归删除，不清理其他成员或历史产物；清理前保持目录归属和符号链接安全检查。清理失败或无法证明失败产物不在可发布树中时，场景不得成功提交。最终可发布树只包含成功成员文件。

正式发布继续链接整组执行目录，因而呈现为 `<channel>/<date>/outputs/<task_id>/<成员名>/<原文件名>`。现有发布实现已经接受同一令牌目录的后代文件，不另建复制/聚合发布层；通过场景文件验收覆盖目录及重放恢复行为。ALL_FAILED 时没有输出映射，不创建正式发布目录。

**取舍：** 不把文件搬到扁平目录或重命名原算法文件；逻辑名加前缀解决下载冲突，物理子目录解决实际写入冲突。仅删除失败成员的字典条目不足以隔离发布内容，因此必须清理本次失败目录。

## Risks / Trade-offs

- [任务 SUCCEEDED 但 ALL_FAILED 容易误读] → 前端指南明确先看 outcome，再按成员 status 展示；列表仅代表任务处理完成，不承诺测量有效或临床结论。
- [顺序执行共享整体时限] → 沿用现有硬时限，整体超时不保存部分结果；验收通过实际消费者覆盖，不能仅用模拟返回证明组合完成。
- [首次成员初始化失败导致全场景提前退出] → 场景延迟初始化、受控延迟制品存在性检查，并覆盖发布后成员文件缺失及不兼容制品行为。
- [复用运行时携带上次任务失败/结果] → 只缓存成功版本资源；输入、错误、评分、指标、目录和结果均为调用内数据，使用不同任务和 A/B/A 版本交错验证。
- [嵌套失败成为敏感信息外泄新通道] → 共享原安全映射、类型化白名单及最终结果校验，使用带私有标记的非法异常和质量对象验证持久化与响应不泄漏。
- [失败成员残留被整目录发布] → 在场景汇总前清理其本次目录，无法隔离则任务失败；验证正式目录内容而不只验证输出字典。
- [已有规范将质量拒绝理解为整个算法终止] → 差量规格明确终止范围是原单算法调用；独立调用语义不变，场景不是绕过成员质量门禁。
- [原算法采样与数值边界并不相同] → 保留各成员规则、质量评分和结果，不趁本次编排修正数值问题；医学准确性和实际采集兼容性不由组合成功证明。

## Migration Plan

1. 部署新增定义、编排和安全映射复用，既有四个独立算法及发布版本继续可用，不应用数据迁移或自动渠道切换。
2. 在隔离联调环境通过现有管理流程创建两个场景 Model，名称分别为统一PPG场景、统一PPG+ACC场景；绑定精确场景 key、空参数、完整制品和匹配指标后发布。模型 ID 与发布版本号由环境实际配置产生，不写死在前端。
3. 用真实任务流程验证 PPG 全成功、部分成功、全失败，PPG ACC 成功与失败；核对详情、指标、文件内容和权限。合成测试制品只验证流程，不代替真实模型数值与临床验收。
4. 前端适配新结构后，在获授权的部署流程中选择场景版本；本变更不自动取消旧模型选择或删除其数据。单算法历史页继续按原版本契约读取。
5. 回退时先停止新增场景流量并切回仍受支持的入口，按现有版本切换规则处理草稿；已提交场景须由支持新 key 的消费者排空，保留其定义和制品供历史读取，不部署无法解释未终结场景任务的旧二进制。

实施验收按 `tasks.md` 的定向验证执行。提案阶段只创建规划产物，不运行数据库写入、模型发布或代码测试。
