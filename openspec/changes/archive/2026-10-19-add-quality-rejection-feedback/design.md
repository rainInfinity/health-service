# Design

## Context

动机与能力范围见 [proposal.md](proposal.md)。本设计适用于当前工作区的纯计算包与 Django 服务包。

已核对的实现约束：

- `health-inference` 没有第三方运行依赖，现有契约使用不可变数据结构，算法通过 `InferenceError` 跨越计算边界。
- `application/execution.py` 当前只生成失败码和固定摘要；未知计算错误码会归并为通用执行错误。
- 持久化失败函数在事务中检查 `RUNNING`、执行令牌和数据库时间判定的有效租约，但当前始终将 `failure_detail` 写为 `None`。
- 本人详情尚未加载 `failure_detail`，公开响应也没有质量字段；列表与详情共用内部记录类型，但通过字段选择和 `include_detail` 区分加载范围。
- 消费者已经捕获 `InferenceError`，停止心跳后检查失权，并只在终态提交成功后记录结果事件和确认消息。
- 现有 API 测试故意在内部明细写入路径和原始诊断，验证响应不得公开；这条隐私边界必须继续成立。
- 数据库设计已有 `INFERENCE.QUALITY_REJECTED`。主任务规格当前只允许安全摘要，本变更的任务增量规格显式增加类型化质量信息这一例外。

这些约束要求同时设计计算契约、写入边界和读取投影，因此本变更需要设计文档。

## Goals / Non-Goals

**Goals:**

- 让有评分与无评分的拒绝共用原因驱动的契约，并在写入与读取时复用相同的原因及明细有效性规则。
- 将私有持久化记录与公开响应分离；任何额外诊断字段都不能因响应扩展而自动暴露。
- 保持既有执行失败入口、返回语义、事务、租约、ACK 和日志字段约定。

**Non-Goals:**

- 不为算法增加实际质检判定、通用阈值、默认分数或成功质量评价，也不改变现有示例的输入与输出契约。
- 不引入动态原因注册、规则引擎、多个拒绝原因的收集机制或质量失败重试流程。
- 不增加公开的任意诊断字段、采集阶段、路径、原始信号或健康资料。

## Decisions

### 1. 使用受控原因与对应明细，不以分数作为共同基类

在 `health_inference/quality.py` 定义受控原因及不可变的质量拒绝数据，沿用纯 Python 数据结构，不引入 Pydantic 或 Django。原因和明细的对应关系在该边界验证。

| 原因 | 明细 | 原因对应的安全提示 |
|---|---|---|
| `LOW_SCORE` | 类型化 `score`、`threshold`，二者必填 | 信号质量评分未达到要求，请重新采集 |
| `NO_VALID_SIGNAL` | `None`，对外为 `null` | 未检测到可用信号，请重新采集 |

`NO_VALID_SIGNAL` 只定义反馈语义，不实现平直信号检测等判定规则。算法只有依据自身明确规则确认没有可用信号时才能使用它，不能将任意预处理失败归入这一原因。

替代方案：所有原因都提供可空的分数，或统一接受任意明细字典。前者让非评分算法被迫使用无意义字段，后者不能表达原因与明细的对应约束，也扩大了泄露风险，均不采用。

### 2. 校验拒绝信息，而不是实现通用评分门槛

`LOW_SCORE` 只接受原生数值，排除布尔值、字符串和非有限值，并要求 `score < threshold`。保留本次实际比较值，不先四舍五入，不统一归一化，不规定所有算法都使用 0–100 量表或阈值 70。

分数等于或高于阈值时，不能构造合法的 `LOW_SCORE` 拒绝；这不代表服务替算法实现质量通过判定，也不保证任务后续成功。未知原因、明细缺失及原因与明细不匹配是契约错误，不是新的采集结论。

替代方案：通用组件接收一个分数并自行推导拒绝原因。该方案会把算法规则混入反馈层，也无法支持无评分原因，因此不采用。

### 3. 专用异常携带拒绝数据，服务决定公开文案

在 `exceptions.py` 增加 `QualityRejectedError`，继承 `InferenceError`，携带通过质量契约校验的拒绝数据，错误码固定为 `INFERENCE.QUALITY_REJECTED`；通过包入口显式导出。

`application/execution.py` 先识别专用异常并验证其受控数据，再构造固定失败码、原因对应的安全摘要以及白名单持久化明细。异常自身的任意正文不参与保存或文案生成。质量数据校验失败按现有 `INFERENCE.EXECUTION_ERROR` 路径处理；只伪造同名错误码的普通 `InferenceError` 也不能绕过契约校验。

仅质量数据的契约校验失败可以转为安全执行失败；数据库和 Redis 异常仍向原有基础设施故障路径传播，不因本变更被吞掉。

保留应用层 `record_task_execution_failure()` 的 `str | None` 返回语义：终态提交成功返回实际失败码，失权返回 `None`。消费者继续复用现有 `except InferenceError` 分支，不为每种原因增加消费逻辑。

替代方案：消费者按原因分别捕获，或直接信任异常的 `safe_message`。前者重复执行权和 ACK 逻辑，后者破坏现有固定文案白名单原则，均不采用。

### 4. 复用失败事务，明细只存放在既有私有字段

持久化失败函数增加显式的 `failure_detail` 参数，并同步调整唯一应用层调用方，不保留平行保存路径。质量失败将原因及类型化明细的白名单序列化结果放在 `failure_detail.quality`；普通失败显式传入 `None`。

继续在同一事务更新失败状态、失败码、摘要、明细、完成时间并清空执行字段，保留行锁、令牌和未过期租约检查。持久化函数继续返回布尔值。

本次不增加数据库字段或迁移，不将质量信息塞入 `result_payload`，不登记指标或权威输出。算法此前产生的中间文件不会因此成为可下载的成功输出，也不新增文件清理策略。

替代方案：新建质量表或将诊断塞入成功结果。当前数据结构已能表达失败明细，新增存储结构无必要；成功结果另受状态约束，不能用来承载失败。

### 5. 详情显式投影，公开 Schema 按原因区分

- 仅 `_TASK_DETAIL_FIELDS` 增加 `failure_detail`；列表字段集合保持不变，内部记录组装仅在 `include_detail=True` 时读取它。
- `TaskRecordData` 增加私有明细，`TaskDetailData` 只增加类型化 `quality_failure`，不向响应传递原始明细。
- `read_user_task()` 先检查状态和失败码，再从私有质量对象中显式选取已声明字段，重建并验证质量拒绝数据。合法值旁的额外字段被忽略，不直接序列化整份 JSON。
- 响应层使用以 `reason` 为区分字段的联合 Schema，使 OpenAPI 明确表达 `LOW_SCORE` 必须有评分明细、`NO_VALID_SIGNAL` 的明细必须为 `null`，而不是开放的字典。
- `TaskDetailResponse.quality_failure` 对外别名为 `qualityFailure`，默认 `None`；非质量失败和其他状态始终为 `null`。
- 历史明细缺失、结构损坏、原因未知或值非法时，不生成质量对象，保留已有安全摘要且不让详情变成 500。查询不重新执行算法，不从当前配置补原因或阈值。

HTTP 查询仍成功返回原有外层包装；业务失败由任务状态表达。列表、输入下载、成功输出下载及账号和渠道归属检查均不改变。

替代方案：直接暴露 `failureDetail`，或只把分数拼进提示文字。前者扩大私有数据边界，后者使客户端依赖文案解析，均不采用。

### 6. 将改动限制在既有职责边界

| 位置 | 责任 |
|---|---|
| 新增 `packages/health-inference/src/health_inference/quality.py` | 原因、不可变明细与契约验证 |
| `packages/health-inference/src/health_inference/exceptions.py` | 专用质量拒绝异常 |
| `packages/health-inference/src/health_inference/__init__.py` | 显式公开算法接入契约 |
| `packages/health-service/src/health_service/application/execution.py` | 安全失败映射与明细构造 |
| `packages/health-service/src/health_service/infrastructure/persistence/tasks.py` | 原子保存与详情字段加载 |
| `packages/health-service/src/health_service/schemas/internal/tasks.py` | 私有记录及类型化详情数据 |
| `packages/health-service/src/health_service/application/tasks.py` | 详情白名单投影 |
| `packages/health-service/src/health_service/schemas/responses/tasks.py` | 公开联合 Schema 和响应转换 |

不增加独立通用失败框架，不修改模型表、配置模板或生产算法注册表，也不保留未落地的 `QUALITY_FAILED` 命名或旧评分专用异常接口作为别名。

### 7. 验证业务边界，不把测试算法当真实质检

新增 `tests/unit/test_inference_quality.py` 验证合法原因、明细组合及非法数值边界。扩展现有任务结果、消费者和任务 API 集成测试，覆盖失败终态、事务回滚、失权、重复消息、HTTP 读取及隐私隔离；普通失败继续验证不保留任意详情。

质量拒绝分支使用隔离的测试算法触发，不修改生产 `hr_br.example`，不依赖真实患者输入或外部权重，测试结束不得污染全局算法注册。测试需要证明状态、ACK、执行次数及公开信息边界，不只比较异常字段的转发或固定提示文字。

实施完成后使用隔离的 PostgreSQL、Redis Stream 和测试算法，实际运行现有 `run_inference` 单轮入口并通过 HTTP 查询同一任务，分别观察有评分和无评分拒绝。该运行只验证反馈通道，不验证医学算法或信号质量判断准确性。

## Risks / Trade-offs

- [新增原因需要跨层同步] → 原因、明细类型、公开 Schema、安全文案及行为测试一并更新，不允许任意原因字符串自动公开。
- [算法缺少明确采集规则] → 本变更只提供契约；接入真实算法时必须提供对应判定证据，不能以捕获某种第三方异常替代规则。
- [历史 JSON 可能包含损坏或私有内容] → 查询显式白名单投影并容错为 `qualityFailure: null`，不将历史内容直接交给响应模型。
- [把业务质量拒绝误当作基础设施故障重试] → 保留现有异常分类和持久化后 ACK 边界，质量拒绝提交后不重跑。
- [联合 Schema 增加少量类型定义] → 用明确的两种响应变体换取契约和 OpenAPI 的可解释性，不引入动态注册器。
- [旧客户端不理解新原因] → 保留原有安全摘要，新增原因只做兼容性扩展，客户端仍可直接展示 `failureMessage`。

## Migration Plan

1. 本变更无数据库迁移或数据回填。实现后按现有部署约定成对升级 Web、消费者和两个工作区包，避免混用版本。
2. 启动升级后的消费者并执行反馈通道运行验证，再开放使用新质量拒绝契约的算法；本变更自身不发布真实质检算法。
3. 历史失败不重新分类、不补评分，也不触发重执行。历史合法质量数据按支持的原因读取，无法解释的明细保持私有。
4. 回滚时按现有流程停止新消费者并恢复成对的旧代码；保留数据库和文件中的既有记录，不删除新增质量 JSON、不回退数据库结构。旧响应不读取该质量明细，仍可展示已保存的安全失败码与摘要。
