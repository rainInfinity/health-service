# 提案

## 背景

仓库目前只有架构和数据库设计文档，尚无可运行的 Django 服务或迁移；自定义用户模型必须在首次建库前确定，不能把项目初始化与数据库模型当作互不相关的后续工作。将既有设计转化为同一变更中的可验证基线，避免先按默认用户建库再迁移的代价。

## 变更内容

- 以 Python 3.13、`uv`、Django 5.2 LTS、Django Ninja／Ninja Extra、PostgreSQL 和 `psycopg` 3 建立可启动的 ASGI 服务与开发验证入口；维护单一、可提交的依赖锁文件，区分 Web 与按需安装的推理依赖。
- 在第一次迁移前配置 `AUTH_USER_MODEL`，建立 `health_service` 的自定义用户模型、抽象审计模型，以及文档定义的 12 张 `health_*` 业务表的 Django ORM 映射与初始迁移。
- 在模型和迁移中落实字段空值语义、外键、唯一／检查约束和必要的初始查询索引；明确数据库不能独自保证的跨表校验、状态转换和并发写入边界。
- 为首次部署和后续变更提供可重复的 PostgreSQL 迁移、配置检查以及关键数据约束的验证依据。
- 本变更不交付注册登录与双 Token API、文件上传、Redis 消费、任务执行、算法推理、旧库数据导入或旧迁移复用；这些行为需在后续变更中实现，不能因为存在表而视为可用。

## 能力

### 新增能力

- `service-bootstrap`：服务可按锁定依赖启动 ASGI 应用，并在配置的 PostgreSQL 上执行首次迁移和配置检查。
- `health-data-model`：用户健康资料、模型与渠道目录、推理任务及结果拥有约定的持久化关系和数据库可执行的完整性约束。

### 调整能力

无；项目尚无已发布的 OpenSpec 能力规格。

## 影响

后续实现将涉及 Python 项目配置、`config` 与 `health_service` 包、数据库迁移、依赖锁文件及其忽略规则；使用 PostgreSQL 作为唯一正式数据库。当前没有既有代码或 API 需要兼容，也不对现有部署承诺迁移旧数据。文档中尚未确定的输入／输出契约、可靠投递、令牌库兼容性和原始健康文件保留政策，不在这次初始建模中补定。
