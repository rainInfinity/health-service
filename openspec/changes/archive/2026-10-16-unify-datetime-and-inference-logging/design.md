# Design

## Context

动机见 `proposal.md`。本变更跨越 API 序列化、日志格式器和独立消费命令，涉及客户端格式兼容与安全日志边界，因此需要设计文档。

- `src/config/settings.py` 已设置 `TIME_ZONE = "Asia/Shanghai"`、`USE_TZ = True`；日志格式器却显式使用 UTC ISO 8601。
- `src/config/urls.py` 使用 Ninja 的 `JSONRenderer`，保留 UTF-8 中文输出；公开的任务和版本 schema 直接声明 `datetime`。
- 当前安装的 Ninja 在 `operation.py` 中调用默认 Python 模式的 `model_dump()`，随后经 JSON encoder 输出；仅给 Pydantic 增加 JSON 模式 serializer 不足以覆盖真实 HTTP 路径。
- `ConsoleApiFormatter` 将所有字段输出为 `key=value`；普通应用日志只保留事件名，任意附加字段都会被丢弃。
- `run_inference` 具备常驻、单轮、租约续约和信号退出逻辑，但没有正常日志调用。失败保存函数先安全映射错误，再以布尔结果表示是否提交。
- `dispatch_task` 对发布失败返回 `False`、对发布时间补记失败返回 `True`，属于既有可恢复语义，不应为了记录日志而改为抛出异常。
- `api-request-logging` 的“仅 stdout、无需可写日志目录”条款与现行 `application-logging` 及实现冲突；本次增量将其对齐到现有双通道行为，不重新设计文件日志。
- `NINJA_JWT` 当前将 Access、Refresh 的有效期分别写死为 7 天、30 天。`issue_token_pair` 是普通渠道、manager 登录和 Refresh 轮换共用的签发入口；项目已提供正整数环境变量读取函数和进程环境优先的 dotenv 加载规则。

## Goals / Non-Goals

**目标：**

- 转换发生在展示边界，API 与日志复用一份北京时间格式规则。
- 接收、取得执行权、终态提交和消息确认保持不同语义，日志不能跨过真实状态边界。
- inference 元数据可关联且受限，普通应用日志仍不接收任意字段。
- 原有请求关联、中文 JSON、安全错误、续约和确认契约保持有效。
- Token 有效期仅在配置入口提取，复用现有签发链路，保持默认期限和存量令牌语义。

**非目标：**

- 不修改数据库字段、内部 schema、JWT 时间声明的编码格式、输入日期格式或算法结果契约；不追溯更改存量令牌的失效时间。
- 不改写现有日志、下载文件、任意 JSON 字符串或用户资料。
- 不新增重试、心跳日志定时器、进度百分比、日志采集服务或配置开关；新增配置仅限两个 Token 有效期环境变量，不增加分渠道期限或热加载机制。
- 不统一 Uvicorn 自身启动横幅、Django admin、第三方日志或管理命令框架的 stderr 文案；本次格式针对应用结构化日志与 JSON 业务回复。
- 不实现多进程安全轮转，也不把日志事件当作可靠审计流水。

## Decisions

### 1. 共享显式时区格式函数，内部保持原有时间类型

在 `src/health_service/` 下增加小型时间格式模块，保存可复用的 `ZoneInfo("Asia/Shanghai")` 与秒级格式规则；API 公开时间类型与日志格式器调用同一函数。对已有带时区时刻先转换时区，再格式化，直接省略小数秒，不四舍五入。

内部继续使用原有 aware `datetime`；数据库租约仍依赖数据库时间，耗时仍依赖单调时钟。不为当前不存在的 naive 时间输入新增兼容推断，不通过修改进程 `TZ` 影响其他组件。

选择共享函数而不是在 schema 和日志中分别 `strftime`，避免两条规则后续漂移；不做字符串正则替换，避免误改用户内容和错过跨日换算。

### 2. 使用公开响应专用日期时间类型，覆盖 Python 模式序列化

在公开响应 schema 的类型模块中定义一个复用的日期时间类型：保留 `datetime` 校验和内部值，使用 Pydantic serializer 在 Python 与 JSON 两种 dump 模式都生成北京时间字符串，并附带与输出一致的 JSON Schema 声明。

将 `schemas/responses/tasks.py` 与 `schemas/responses/catalog.py` 所有公开日期时间字段迁移到该类型；可空字段仍为该类型与 `None` 的联合。内部 schema 不变，不以字符串替换数据库投影。`ApiResponse` 嵌套模型、列表和分页自然沿用字段 serializer，无须递归遍历任意字典。

JSON Schema 明确为 `string`，匹配 `^[0-9]{4}-[0-9]{2}-[0-9]{2} [0-9]{2}:[0-9]{2}:[0-9]{2}$`，附 `Asia/Shanghai` 说明和秒级示例，不声明 `format: date-time`。`birthDate` 保持原 `date` 类型及日期声明。

保留现有 JSON renderer 和 `ensure_ascii=False`，不安装全局 JSON encoder，不改变请求 schema。替代方案是只定制 renderer，但这会把 OpenAPI 声明与实际输出分散到两处，而且无法可靠处理上游已经转为字符串的值；响应类型方案能同时约束输出和文档。

### 3. 先构造安全日志条目，再分别呈现 console 与 JSON

沿用 `_structured_entry` 的安全字段构造流程，将时间值切换为共享北京时间格式。JSON formatter 保留所有原键及类型。

console formatter 显式输出无键时间、无键级别；有 `status` 时将其作为第一个键值字段，其余字段按固定次序输出且不重复。现有键值编码保留：含空白或控制字符的值仍正确转义，不因新的时间前缀破坏单行约束。仅级别值高亮，不重新加上 `level=`；事件与 HTTP 状态高亮规则保持不变。

解析方按固定宽度的日期时间前缀、级别及后续键值字段解析，不再对整行直接运行仅接受 `key=value` 的解析器。迁移三个现有 API 日志测试文件中的解析方式，继续验证请求关联、隔离、安全性及双通道一致性；删除仅钉死旧前缀或旧 ISO 形式的断言，不为旧格式保留兼容路径。

### 4. inference 使用独立事件与字段白名单，复用现有 handler

使用 `health_service.inference` logger，继承既有 `health_service` 的 stdout 和 `application_file` handler，不添加重复 handler，也不落入 API logger。

为 inference 定义固定事件集合及专属字段集合；只有该 logger 命名空间与合法事件组合可以保留这些字段。其他应用事件仍只保留时间、级别和稳定事件名，不能借机透传任意 `extra`。

| 字段 | 含义与边界 |
| --- | --- |
| `consumer` | 消费者关联标识，按单行有界字符串编码，不借此记录连接配置 |
| `mode` | 固定值 `once` 或 `continuous` |
| `taskId` | 已验证的正整数任务标识；无法解析时省略，不回显原值 |
| `messageId` | 合法 Redis Stream 消息标识 |
| `durationMs` | 基于单调时钟的任务执行耗时，维持毫秒级精度 |
| `errorCode` | 已安全映射的任务失败码，仅用于已提交失败结果 |
| `reason` | 来自固定集合的运行诊断，不能传入任意异常内容 |
| `exceptionType` | 可用时记录受控异常类型，不序列化正文、堆栈或异常对象 |

不把 API 的 `requestId`、用户、渠道上下文复制到消费者；不输出执行令牌、租约 token、原始消息字段或文件路径。成功关联只依赖消费者、任务和消息标识，不依赖新的持久化字段。

### 5. 在真实边界发出事件，不以日志驱动业务

| 事件 | 级别 | 发出边界 |
| --- | --- | --- |
| `inference.worker.starting` | INFO | 参数检查通过后、连接与消费组初始化之前 |
| `inference.worker.ready` | INFO | 消费组初始化及首轮数据库补发扫描成功后、首次消费之前；只输出一次 |
| `inference.message.received` | INFO | 已接收到消息；只加入安全可解析的标识 |
| `inference.task.started` | INFO | 有效执行权领取成功后、计算开始前 |
| `inference.task.succeeded` | INFO | 成功结果与终态提交成功后、尝试消息确认之前 |
| `inference.task.failed` | ERROR | 失败终态提交成功后，携带实际安全失败码 |
| `inference.task.lease_lost` | WARNING | 续约失权或终态写入被所有权条件拒绝时，不输出当前执行的终态事件 |
| `inference.dispatch.failed` | WARNING | 发布失败或派发时间补记失败，使用固定原因，保留既有返回值与补偿资格 |
| `inference.worker.error` | ERROR | 数据库或 Redis 故障导致当前命令错误退出；有任务上下文时保留关联标识 |
| `inference.worker.stopped` | INFO | 单轮完成或信号关闭后的正常清理完成；异常退出不输出正常停止 |

重复终态、无效消息和有效租约占用仍走原确认或保留路径，不增加 `task.started`；接收事件足以表明消息被看见。正常空轮询、续约和补发空扫描不增加周期 INFO。无需为当前算法无法提供的内部计算进度制造假进度。

心跳线程的失租及异常需要保留固定原因，并在现有执行协调点输出安全诊断；不能因为日志加入新的续约尝试，也不能从线程输出原始异常。任务上下文随本次消息处理传递，不存放到跨消费者共享的全局可变状态。

### 6. 直接复用安全失败映射，不重新解析异常或多查数据库

现有应用层 `record_task_execution_failure` 已知道安全失败码，但返回布尔值，消费者无法可靠区分所有失败原因。将该内部应用层结果改为 `str | None`：失败终态提交成功时返回实际已映射并保存的失败码；提交被拒绝时返回 `None`。持久化层的布尔契约不变。

消费者在收到非空安全码时记录 `task.failed`；成功保存路径仍使用原布尔结果。实施时一次迁移该函数全部调用方和相关测试，不保留布尔兼容别名。不新增数据库读取，不复制 `_safe_failure_fields` 的映射，也不从 `InferenceError.code` 直接拼接日志失败码。

`dispatch_task` 只补充固定诊断，不改变发布失败 `False`、补记失败 `True` 的行为。数据库错误或 Redis 确认错误仍沿原错误退出路径传播；成功提交后的确认失败只能新增基础设施错误事件，不能反向记录业务失败。

### 7. Token 有效期在启动时从环境配置读取

沿用现有 `_positive_integer_env`，在 `src/config/settings.py` 的配置入口读取以下可选值，再以 `timedelta(seconds=...)` 传给 `NINJA_JWT`：

| 环境变量 | 默认秒数 | 对应设置 |
| --- | --- | --- |
| `JWT_ACCESS_TOKEN_LIFETIME_SECONDS` | 604800 | `ACCESS_TOKEN_LIFETIME` |
| `JWT_REFRESH_TOKEN_LIFETIME_SECONDS` | 2592000 | `REFRESH_TOKEN_LIFETIME` |

两项独立配置，无需同时设置；不额外要求 Refresh 时长必须大于 Access。缺省保留既有 7 天／30 天；显式空值、零、负数、小数或非数字值沿用正整数配置的明确启动错误，不能静默回退。进程环境覆盖 `.env`，显式空进程值也不能被文件中的合法值替换。

配置只在进程启动时读取，调整后需重启签发服务。普通渠道和 manager 登录、成功的 Refresh 轮换都通过现有 `issue_token_pair` 使用同一组当前配置，不在业务函数重复计算有效期或引入另一套配置。保持签名密钥、渠道绑定、轮换撤销及权限检查不变。

已签发令牌继续依其自身 `exp`、签名、撤销及账号状态判断；缩短新配置不提前撤销旧令牌，延长配置也不延长旧令牌。`exp`、`iat` 继续使用 JWT 标准数值格式，不经过北京时间展示函数。选择环境变量而非数据库配置或 API 管理入口，符合项目现有部署方式，不引入持久化和热更新复杂度。

实施时同步 `.env.template` 的单位、默认值及注释，以及 `docs/development.md` 的配置表、登出后 Access 边界和令牌维护说明，将固定有效期改为“默认值／以签发时配置为准”。不修改实际 `.env`。

配置测试沿用隔离进程方式，并将两个新变量纳入测试环境过滤，避免开发机设置污染用例。实际签发验证采用隔离进程加载非默认配置，经真实登录、刷新接口解码验证签名后的 JWT，核对 `exp - iat`；不只检查设置字典或手动构造的令牌。存量令牌场景使用受控时钟或固定声明验证，不依赖真实等待，不让 JWT 库的全局设置缓存污染其他测试。

## Risks / Trade-offs

- **客户端解析破坏性变更** → API、OpenAPI、开发示例和采集解析规则一起切换，不保留旧格式双写；客户端应按北京时间解释新字符串，不能交给浏览器推断宿主时区。
- **时间字符串不再携带时区或小数秒** → 在字段说明及文档固定标明 `Asia/Shanghai`；内部精度保留，任务排序仍遵循原数据库规则，不能用展示字符串判断并发先后。
- **混淆计算结束、事务提交与确认成功** → 事件严格落在状态边界；成功事件只表示终态已提交，确认失败另记，不新增逐次 ACK 成功日志。
- **日志扩展泄露健康资料或任意异常** → inference 专属白名单与固定事件/原因集合；对无效标识省略原值，继续执行敏感哨兵验证。
- **日志展示日与归档日期不同** → 本次仅改变内容时区；文档明确现有轮转仍按宿主机本地午夜，不暗中修改归档规则。
- **Web 与 inference 同时写同一轮转文件** → 沿用现有每进程独立目录约束，在开发与部署命令中分别使用 `LOG_DIR=logs/web`、`LOG_DIR=logs/inference`；不增加配置项或多进程轮转实现。
- **事件输出不是持久任务事实** → 数据库仍是任务状态来源，日志可能在进程中断时缺失，不能用日志替代补偿扫描或租约判断。
- **Token 配置误配或测试环境泄漏** → 复用正整数读取规则，明确变量名和启动错误；隔离测试清除两个新环境变量，真实签发路径验证各渠道登录和刷新。
- **缩短配置被误认为立即撤销已有令牌** → 文档明确只影响重启后的新签发；已有令牌仍按自身 `exp` 及现有撤销、账号检查处理，回滚同样不追溯修改令牌。

## Migration Plan

1. 实现共享时间规则、公开响应类型和日志格式；同步全部公开日期时间字段与现有消费者调用方。
2. 迁移原日志测试解析方式；以真实 HTTP 检查 UTC 转北京时间、跨日、空值、纯日期与嵌套分页，并核对 OpenAPI。
3. 使用隔离 PostgreSQL、Redis Stream 和文件目录运行真实单轮消费者：空队列、示例成功、合法计算失败；观察 stdout 与 JSON 文件、持久终态及确认结果。
4. 使用现有工作流测试补充或扩展失租、终态提交失败及成功后确认失败等状态边界验证；常驻消费者实际启动并发送停止信号，观察就绪及退出。验证输出中不含敏感哨兵，正常空闲不刷 INFO。
5. 提取两个 Token 有效期配置并同步 `.env.template`，验证缺省、独立覆盖、dotenv 优先级、非法输入以及真实登录和刷新签发；用受控时钟证明配置切换不改变旧令牌的 `exp`。
6. 验证通过后更新 `docs/development.md` 的格式、时区、消费者日志、独立 `LOG_DIR` 命令及 Token 配置与生效边界，说明采集端与客户端同步切换；不新增独立技术文档。
7. 部署时同步更新消费新时间或 stdout 格式的客户端、采集器，并有序重启 Web 与 inference；如需非默认 Token 有效期，部署环境显式提供两个变量。历史文件不重写，无数据库迁移。需回滚时一起回退服务代码、格式消费者及有效期配置，保留数据库、Redis 未确认消息和存储文件；回滚不修改已签发令牌的 `exp`。
