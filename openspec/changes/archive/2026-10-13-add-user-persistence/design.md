# Design

## Context

动机见 `proposal.md`。本变更涉及应用用例、持久化、内部数据及 HTTP 契约多个模块，并包含事务与并发边界，满足编写设计文档的条件。

当前 `application/accounts.py` 同时完成注册验证、ORM 创建和 PostgreSQL 用户名约束识别；`application/profiles.py` 直接返回 `Profile`，并通过先锁账号、再锁资料保证首次创建及 PATCH 合并的串行化。`api/v1/users.py` 用 `by_alias=True` 导出嵌套病史，导致 HTTP 别名进入存储。请求模型已有下划线 Python 字段，响应中的病史则是普通字典，不能依赖外层 Schema 自动转换其键。

数据库设计及 `tests/integration/models/test_profiles.py` 已采用下划线病史键，部分 API 测试却用驼峰键建立数据库数据。用户已明确当前是无存量数据的开发阶段，不需要迁移。模型、外键和唯一约束均保持不变。

## Goals / Non-Goals

**Goals:**

- ORM 的查询、行锁、创建、保存及约束识别由具体持久化模块负责；应用层决定事务范围和业务规则。
- 持久化与应用用例交换已求值的内部数据，注册及资料用例不向 API 返回 ORM 实例。
- 病史只在 HTTP 边界使用外部命名，内部与存储使用已定义的下划线键，不丢失 PATCH 的字段存在性。
- 保留缺失资料、空 PATCH、并发首次创建和并发病史合并的实际行为。

**Non-Goals:**

- 不把 Django 认证接口、第三方 JWT 黑名单和业务数据访问强行合成一个仓储。
- 不建立领域实体镜像、通用 CRUD、同步／异步双份 DAO 或自定义事务框架。
- 不为资料命名问题增加数据库迁移、旧键兼容或清理数据的步骤；不修改任务快照、算法输入输出或其他业务 JSON。

## Decisions

### 1. 采用具体模块级函数

新增 `infrastructure/persistence/accounts.py`、`profiles.py` 和 `exceptions.py`，沿用现有应用模块的函数组织方式。接口按当前用例确定，不接受任意模型、任意 ORM lookup 或任意权限字段。

| 模块 | 操作 | 输入／结果与前置条件 |
|---|---|---|
| accounts | 创建普通账号 | 接收已验证用户名和密码，通过 Django `create_user()` 哈希密码；固定手机号未绑定及普通权限，返回 `AccountSummary` |
| accounts | 锁定账号 | 接收用户 ID，在调用方已有事务中锁定账号；不向调用方返回 ORM 对象 |
| profiles | 读取资料 | 接收用户 ID，可在事务中执行锁定读取；返回 `ProfileData` 或 `None` |
| profiles | 创建资料 | 接收用户 ID 和规范化字段，可用于注册空资料与首次填写；返回内部资料数据 |
| profiles | 更新已有资料 | 接收用户 ID 和已合并的变更字段；调用方已锁定账号和现有资料，不自行提交事务 |

不照搬旧项目 `BasicDO/AsyncBasicDO`：这些方法主要重复 ORM，且旧更新逻辑忽略 `None`，无法表达本项目的明确清空。也不引入仅有一个实现的仓储接口或依赖注入容器。

### 2. 内部结果使用最小 Pydantic 数据模型

在 `schemas/internal/accounts.py` 定义 `AccountSummary`，只包含 `user_id`、`username`；在 `schemas/internal/profiles.py` 定义 `ProfileData`，包含归属 ID 和当前公开资料所需字段，保留日期与 Decimal 类型。内部类型不包含 Request、HTTP 别名、ORM 实例、密码、权限或可触发查询的属性。

`ProfileData.history_json` 保持可空字典，以保留未涉及的扩展内容；已定义标记只使用下划线键。资料缺失由 `None` 表达，而不是用空资料结果掩盖记录是否存在。

沿用请求 Schema 的验证能力，API 用 `model_dump(exclude_unset=True, by_alias=False)` 得到规范化 PATCH 更改集；不为完全相同的用例输入再增加 DTO。病史合并时构造新的字典，不原地修改读取结果。

仅在持久化读取处映射 ORM 数据，不另复制领域 User/Profile 实体。注册和资料 API 只转换内部结果；`request.user` 仍可作为 Django 认证得到的上下文，不要求重写本人账号查询或认证后端。

### 3. 应用层持有一个同步事务

注册用例保留用户名规范化、字段验证及 Django 密码验证；这些认证能力可以使用用户模型元数据，但不在应用层执行 ORM 查询或保存。验证通过后，应用层开启 `transaction.atomic()`，依次调用持久化创建账号和空资料，成功后返回 `AccountSummary`。

持久化仅在明确命中 PostgreSQL 用户名唯一约束时抛出专用冲突错误。应用层在退出事务、完成回滚后将其转换为已有 `UsernameAlreadyExists`；其他数据库错误原样传播，不全部包装为重复用户名。保留数据库唯一约束作为并发裁决，不增加先查再插入。

资料 PATCH 用例在同一个事务内完成：锁账号，锁定读取资料，计算合并字段，创建或更新资料，返回内部结果。缺失资料且更改集为空时返回 `None`，不创建记录；已有资料且更改集为空时返回现有数据，不保存、不刷新修改时间。

账号行是资料不存在时的稳定锁点，不能仅保留资料行锁。锁定读取必须在调用方事务内执行；所有资料写入统一保持账号在前、资料在后的锁顺序。并发请求在获取锁后读取最新资料并合并，不能使用加锁前的快照。

创建继续走模型保存以维护审计时间。更新已存在资料采用定向 `QuerySet.update()`，仅写业务变更字段并显式写入 `updated_at`；没有新的操作人输入时保留已有操作人字段，不引入隐式 Request 上下文。依据已锁定的内部数据及变更构造结果，不为返回结果无条件重复查询；若更新未命中预期记录，则按异常传播而不静默返回成功。

异步 HTTP 入口继续用一次 `sync_to_async(..., thread_sensitive=True)` 执行完整同步用例，事务内部不拆成多个异步调用。

### 4. HTTP 边界显式转换嵌套病史

入站沿用 `StructuredHistoryPatch` 的 `isDiabetic`、`isHypertensive` 别名，导出时使用内部字段名并保留 `exclude_unset=True`。`False`、显式 `None` 和缺席必须分别保留；删除当前 `users.py` 中重新以 `by_alias=True` 导出病史的路径。

应用层用下划线键计算病史合并：缺席不变，键值为 `None` 删除对应键，其他布尔值保存，整个字段为 `None` 清空。资料标量字段继续按是否提交决定更新，不使用 `exclude_none=True`。

出站在 `schemas/responses/profiles.py` 放置资料响应转换，显式将两个已定义的下划线键映射为外部驼峰键，保留其他未涉及键及其内容；API 调用该转换，不导入 `Profile`。不对任意扩展 JSON 实施通用递归 snake_case/camelCase 转换，也不支持旧驼峰存储键回退。

病史响应继续使用字典表示，避免为了声明两个字段而丢掉现有扩展内容；通过响应字段的 JSON Schema 元数据描述两个可选的外部病史标记及扩展属性。转换只输出实际存在的键，不为缺失键填充默认 `None` 或 `False`。外层资料未填写字段继续完整返回，不开启会删掉这些字段的全局 `exclude_unset` 序列化。

### 5. JWT 存储边界保持原样

密码登录继续调用 Django `authenticate()`。`infrastructure/auth/tokens.py` 的令牌行锁、账号可用性重检、黑名单写入及原子轮换属于第三方认证适配的完整协议，继续留在同一封装内；不借本次分层拆散 Refresh 的事务和锁顺序。

### 6. 验证关注行为而非分层接线

调整现有 `tests/integration/api/test_user_accounts.py`：HTTP 输入输出保留驼峰，数据库夹具、应用用例直接调用及存储断言改用下划线。保留按键合并、扩展内容、缺席/null/false、渠道与归属隔离、既有资料并发更新及 Refresh 并发轮换的行为覆盖。

在 `tests/integration/users/` 按注册与资料职责补充真实 PostgreSQL 回归：资料创建失败时注册回滚；资料不存在时两个连接并发提交不同字段／病史键，最终只有一份资料且两组更新均保留。故障注入仅制造真实事务失败，不以 mock 返回值证明数据一致性。

不新增检查 import 路径、源码文本或函数转发的测试。内部结果的无 ORM／无惰性求值边界用一次性验证检查，开发完成后不保留临时脚本。实际 ASGI 冒烟覆盖注册、登录、PATCH、跨渠道读取及数据库键核对，并读取 OpenAPI 验证外部命名。

## Risks / Trade-offs

- [内部 DTO 增加一次数据投影] → 只投影所需字段，不复制完整账号，不建立领域实体镜像，不额外重查结果。
- [字典响应不会自动转换嵌套别名] → 明确限定两个已定义键的映射，验证响应与数据库键不同且语义相同，OpenAPI 与响应一致。
- [序列化默认值可能制造未知病史键] → 转换仅输出实际存在键，验证缺失与 `False` 的差别；不全局改变外层资料序列化。
- [资料不存在时无法取得资料行锁] → 保留账号行锁，并用并发首次填写验证唯一性及不丢更新。
- [定向更新绕过 `AuditModel.save()`] → 显式更新修改时间，保留创建时间与未涉及字段，空 PATCH 不写库。
- [旧驼峰内部调用方失效] → 同步切换全部当前调用方与测试夹具，不保留别名兼容；外部 HTTP 请求命名不变。

## Migration Plan

不执行数据或表结构迁移。当前无存量数据的前提由用户明确给出，本变更不增加迁移文件、清库、暂停写入或旧键冲突处理步骤。

实施按内部类型与持久化、应用用例、HTTP 转换、行为验证和文档更新顺序完成，并作为同一代码变更交付。开发阶段若需回退，回退这一完整代码变更即可；本设计不提供旧版本与新版本混用或回退后继续解释新格式数据的保证，不自动改写数据。
