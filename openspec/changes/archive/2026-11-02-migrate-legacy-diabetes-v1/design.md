# Design

## Context

动机与范围见 `proposal.md`。旧入口为 `../nxhe-backend/src/models/services/diabetes/main.py`，预处理工具位于同目录 `utils/ppg.py`。旧实现把输出路径存于模型实例，在 `preprocess` 更新质量后仍写波形并提取特征；新实现不能直接复用旧业务模型类。

当前项目已具备 `OfflinePipeline`、`AlgorithmDefinition`、`VersionResources`、共享单块 PPG 解析、ONNX Runtime 及迁入的 pyPPG。血氧算法提供资源校验、阶段隔离、指标和输出组织的参考结构，但其九通道滑窗特征与本算法整段统计不相同。

本轮只读探针观察到 `var/old-assets/diabetes-latest-diabetes.onnx` 可由现有 ONNX Runtime 加载：输入 `input` 为 `tensor(float)`、形状 `[None, 918]`；输出 `label` 为 `tensor(int64)`、形状 `[None]`，`probabilities` 为 `tensor(float)`、形状 `[None, 2]`。自定义元数据为空。本次直接使用该文件作为迁移制品，不核验模型制品来源；加载成功仍不证明正类映射、数值兼容性或临床有效性。当前候选样本目录只有血压采集文件，尚无已核验的旧糖尿病完整执行基线。

## Goals / Non-Goals

**Goals:**

- 在当前服务中独立执行固定版本计算，不依赖旧框架、ORM 或实时用户资料。
- 将数值基线与资源契约固定到实现修订；门禁、预测、分类和输出有明确失败边界。
- 用实际采集输入证明旧新兼容，以真实任务链路证明可发布、可执行、可查询及受保护下载。

**Non-Goals:**

- 不将其他算法的资源加载器或特征模块提前抽象成通用框架。
- 不为风险分类新增数据库字段、专用接口或分类指标类型。
- 不改变共享 pyPPG 与依赖来顺带修复旧特征；若兼容问题需要改变已确认计算契约，先停止并重新确认，不悄悄放宽要求。

## Decisions

### 1. 使用独立算法模块，复用现有阶段与版本资源

在 `packages/health-inference/src/health_inference/algorithms/ppg_active_offline_diabetes_v1/` 按现有模式组织输入、预处理、质量、特征、资源、推理、后处理和输出，更新受控注册入口。使用 `OfflinePipeline` 的门禁顺序，特征计算放在质量通过后的推理阶段，输出文件最后生成。

资源只持有模型会话、校验后的输入输出名称和类别映射。处理后信号、918 维特征、评分、概率、分类和输出路径全部为调用内数据。绑定固定版本，不在任务执行时读取渠道当前版本。

不搬旧 `DiabetesModel`：其共享路径和旧业务对象违反调用隔离，也不具备门禁后才计算和输出的保证。

### 2. 固定旧版 PPG 数值链，不复用血氧特征

输入复用共享 `load_ppg` 的单块、有限性、时间轴与通道组约束，再校验滤波所需长度和采样率。不插值、补齐、排序或重采样采集输入。RGB 取 `-avgR/255`；YUV 使用旧 BT.709 红通道 `-(avgY + 1.5748 × (avgV - 128))/255`。采样率按旧均值间隔规则保留两位小数；二阶 0.75–4 Hz 带通、`filtfilt`、总体标准差 z-score，质量调用使用 `int(fs)`。

质量阶段以实际评分均值乘 100 对比 70；非法评分是执行错误，不是低分或默认无可用信号。只有明确低于阈值才报告 `LOW_SCORE`。

质量通过后，对整段清洗 PPG 连续三次 `np.gradient` 形成 vpg、apg、jpg；沿用 `load_signal`、旧特征点修正项 `on/dn/dp/v/w/f` 和生物标志物计算。统计组顺序固定为 `derivs_ratios → ppg_derivs → ppg_sig → sig_ratios`，每组按统计行优先、特征列次之展开，再拼接为 `(1, 918)` 的 float32 输入。

特征有序名称和统计行顺序作为代码内修订基线校验，不新加可随模型制品任意重排的清单。维度检查不足以防止列含义错位。优先使用已迁入 pyPPG，不直接调用血氧特征模块。

### 3. 核对模型兼容性和退化特征，不追溯制品来源

直接使用 `var/old-assets/diabetes-latest-diabetes.onnx`，不要求模型制品来源证明，也不将其作为发布验收前置条件。记录旧源码、共享 pyPPG、模型和样本的 SHA-256 及依赖版本仅用于固定数值基线，不用于证明来源。检查 ONNX 分类器类别属性并与旧推理代码核对，确认第二列的目标类别映射后绑定；不要求额外来源说明，也不由 `label` 输出猜测医学含义。兼容性或类别映射不匹配仍须明确失败，不替换模型或编造概率。

旧 pyPPG 统计会过滤单项 NaN，并可能在样本不足时留下缺失统计或异常。必须在基线阶段核对实际 918 列、缺失值位置及 ONNX 对这些值的行为：有明确旧版缺失特征处理且模型支持时按其保留；未证实的非法特征按执行失败处理，不进行额外填零、删列、默认预测或泛化异常兜底。若退化行为无法证明，不能宣称全链迁移完成。保留质量拒绝、输入错误和程序错误的既有区分。

资源加载校验唯一 float32 矩阵输入、918 列及相容概率矩阵输出，显式绑定校验后的目标概率节点，不照搬旧代码的输出列表下标。允许存在旧模型 label 输出，但不把它用于三档风险分类。元数据不匹配作为制品错误；运行结果形状或数值错误作为 `RESULT.INVALID_OUTPUT`。

### 4. 三档分类是固定服务端后处理，不覆盖原始概率

单任务预测要求恰好一个目标类别概率；先确认有限且属于 `[0, 1]`，然后保留 `prob` 原值。另计算与 ECMAScript `Number(prob.toFixed(2))` 等价的分类比较值，按增量规格生成整数 `risk_level`。不新增计算参数，不在客户端重算，不使用 ONNX 二分类 label 代替产品三档规则。

不能直接使用 Python `round` 或先把浮点数转十进制字符串再舍入：必须按原 binary64 数值实现非负域内与 `toFixed(2)` 相同的舍入语义，并与真实 JavaScript 对照。浮点容差只用于旧新计算对照，分类比较不得引入 epsilon。

本轮使用 Node 执行旧端表达式已确认：0.654/0.655/0.659 的分类为 0/1/1，0.754/0.755/0.759 为 1/2/2；0/0.66/0.76/1 为 0/1/2/2。实施测试还需覆盖边界相邻浮点值，不能仅测试示例常量。

### 5. 沿用现有结果、指标与文件契约

完整 payload 沿现有成功结果结构包含 `prob`、`risk_level`、实际质量信息及身份信息。算法结果校验器核对概率合法、分类为整数 0/1/2 且与概率后处理一致。

概率指标采用 `MetricContract("diabetes_probability", "number", "ratio")`，保持 0–1 原始量纲，不把比例和百分数混用。`risk_level` 放在完整 payload 中，不扩展指标类型体系。版本可以按既有规则选择是否投影概率，但无论是否投影，完整结果都必须有概率和分类。

`processed_ppg` 沿用时间轴与清洗信号 CSV 输出约定，只向传入的本次执行目录写入，服务端复用已有成功登记、发布及下载权限。没有合法最终结果就不组织成功输出。文件名不携带版本推断，不向 payload 暴露本地路径。

## Risks / Trade-offs

- [模型输入输出或类别映射不匹配] → 不核验制品来源；保留输入输出结构、目标概率列和真实模型调用检查，兼容性检查失败不得继续预测。
- [pyPPG 统计缺失及广泛异常捕获可能掩盖故障] → 用固定样本记录逐列值和退化行为，限制兼容处理为有证据的旧规则；禁止静默补零。需要改动共享库时先评估已发布算法基线，超出范围另行确认。
- [共享解析和依赖产生数值漂移] → 对照波形、评分、特征和概率，先定位漂移再确定最小容差；不能只比较最终分类或放宽容差。
- [旧端舍入使阈值前的概率提前进入下一档] → 为兼容保留该行为，测试实际 JavaScript 及阈值相邻浮点值；原始概率不受舍入影响。
- [沿用旧分档可能被误读为已校准风险] → 文档和接入说明明确其为旧产品规则，不输出浓度或确诊声明，不宣称临床验证。
- [当前血压迁移仍在进行] → 不依赖其未完成实现或修改其制品；集成时使用当时已存在的公共运行时，检查既有算法回归。

## Migration Plan

1. 直接使用指定模型制品，完成输入输出兼容性、类别映射、特征缺失行为与实际采集样本旧版基线核验；不核验模型制品来源，数值兼容性验收不得用合成探针替代。
2. 实现独立算法、后处理与注册，增加真实行为边界回归；不自动创建业务模型、发布版本或切换渠道。
3. 在隔离测试数据和存储中通过现有发布链创建配套版本，跑实际输入的完整计算，对照旧新版数值，并执行任务上传、提交、消费、查询、下载与权限检查。合成模型只能辅助隔离测试，不能替代真实模型验收。
4. 验收后更新 `docs/development/algorithms/ppg-active-offline-diabetes-v1.md` 和 `docs/frontend-integration.md`，记录契约、基线、依赖和实际证据；删除一次性验证脚本。正式渠道发布与选择按独立授权执行，不属于自动部署动作。
5. 回退只撤回新任务的渠道选择，禁止删除仍被渠道或未终结任务引用的资源、算法标识、制品及历史结果；已提交任务继续按冻结版本解释和执行，不重写历史分类。
