# Spec Delta

## Purpose

让 ASGI Web API 的正常请求与异常能够通过服务端请求标识可靠关联到结构化日志，便于排查故障，同时避免把登录凭证、用户健康资料等敏感内容写进日志或误认为已具备持久留存保障。

## ADDED Requirements

### Requirement: 每次请求具有独立的服务端标识
系统 MUST 为每次 API 请求生成不可被未经可信客户端任意覆写的 `requestId`，并使该标识可用于关联响应头、JSON 回复、请求完成日志及同次请求的内部异常日志；并发请求的上下文 MUST 彼此隔离。

#### Scenario: 成功与失败关联
- **WHEN** 两个不同的 API 请求分别成功和失败
- **THEN** 每个请求的 `X-Request-ID`、JSON 回复的 `requestId` 与该请求日志一致，两个请求使用不同标识

#### Scenario: 并发请求互不串扰
- **WHEN** 两个账号在不同普通渠道并发访问 API，且一个请求发生异常
- **THEN** 两份请求日志各自记录正确的请求标识、渠道和可用的用户 ID，异常日志只关联发生异常的请求

#### Scenario: 客户端伪造关联标识
- **WHEN** 不受信任的客户端自行提供请求标识请求头
- **THEN** 服务端不直接使用该值覆盖自身用于回复及日志关联的标识

### Requirement: 结构化请求结果日志
系统 MUST 为 API 请求输出可解析的结构化完成记录，至少包含 UTC 时间、级别、`requestId`、HTTP 方法、可用的路由模板、HTTP 状态及耗时；鉴权后可安全记录用户 ID 和普通渠道，业务错误码可用时记录其稳定值。

#### Scenario: 匿名请求与鉴权请求
- **WHEN** 一个匿名登录请求和一个有效 Access 的本人资料请求完成
- **THEN** 两者各有一次可关联的请求完成记录；前者不虚构用户 ID，后者可记录用户 ID 与实际普通渠道

#### Scenario: 未匹配路由或已知客户端错误
- **WHEN** 客户端请求未知 API 路径或触发已知校验错误
- **THEN** 日志记录真实的 HTTP 404 或 422 与请求标识，不需要解析响应正文才能判断状态

### Requirement: 未预期异常具有受控内部诊断
系统 MUST 在未预期的 API 失败时记录与请求完成日志相同的 `requestId` 和受限的内部异常类型／堆栈定位信息；同一异常 MUST NOT 被多个应用异常处理层重复记录，客户端仅收到统一的通用错误回复。

#### Scenario: API 内部失败
- **WHEN** 请求触发未预期的服务器异常
- **THEN** 请求完成日志体现 HTTP 500，并存在一次同标识的内部错误定位记录；响应不包含堆栈或原始异常信息

### Requirement: 日志不包含敏感请求与回复内容
系统 MUST NOT 将请求／响应正文、密码、Access／Refresh Token、Cookie、手机号或健康资料写入应用请求和异常日志；不得从未经可信代理配置验证的转发 IP 头推断真实客户端身份。

#### Scenario: 带敏感内容的认证与资料请求
- **WHEN** 登录请求包含密码、`Authorization` 头携带令牌，或资料请求包含病史内容
- **THEN** 请求及异常日志仅保留安全元数据，不含这些值、原始查询字符串或响应体

#### Scenario: 不可信转发 IP
- **WHEN** 客户端发送自行设置的 `X-Forwarded-For`
- **THEN** 日志不会将该头的任意内容认作已验证的真实来源地址

### Requirement: 应用日志输出到标准输出
系统 MUST 将 Web API 应用日志输出到标准输出以供运行环境采集；本阶段 MUST NOT 以进程内定时滚动文件或未部署的采集器冒充已提供日志持久保存。

#### Scenario: Web 进程输出日志
- **WHEN** 以 ASGI 方式启动服务并调用一个 API 请求
- **THEN** 可从进程标准输出读取结构化请求日志；应用不要求可写的相对 `logs/` 目录，也不承诺没有外部采集时的持久留存
