# 设计

## 背景与约束

动机见[提案](proposal.md)，可观察行为见 [api-request-logging 规格](specs/api-request-logging/spec.md)。现有 `config.settings` 无 `LOGGING` 配置或应用请求日志，Web 以 ASGI／Uvicorn 启动。旧项目的按日文件滚动、`threading.local()`、未验证的代理 IP 与解析整个回复体取业务码不适合新服务；`unified-api-responses` 将读取本变更提供的请求标识。

## 目标与非目标

**目标：** 在 API 请求、统一回复与内部异常之间建立同一标识，输出可解析且默认不含敏感值的结构化访问／错误日志，并在异步请求间隔离上下文。

**非目标：** 不提供本地文件轮转、外部日志平台或具体留存期；不创建尚不存在的推理命令、不把日志替代数据库审计字段、不记录请求或响应内容。

## 技术决策

### 1. 单一请求入口持有标识和安全上下文

在覆盖 `/api/v1/` 的异步兼容 Django 中间件入口生成不可预测的服务端 `requestId`，不采信客户端的 `X-Request-ID` 为权威值。用每请求属性和必要的 `ContextVar` 传递标识、安全的路由／用户元数据；请求结束时在 `finally` 重置上下文，避免 ASGI 并发交错或后续请求继承。入口用单调时钟计算耗时，结束时只输出一次请求完成事件，并将 `X-Request-ID` 加入该 API 回复。未知路径或早期错误也经此入口，以便 404／500 可关联。

渠道只在确认为五个普通 label 后记录，账号 ID 由已验证鉴权结果写入上下文；匿名请求不猜测用户名或用户 ID。路由字段优先使用框架提供的匹配模板或明确注册的模板，未匹配时使用固定标记，不写原始 URL、路径参数和查询字符串。错误层只提供稳定业务码与状态，日志层读取安全元数据，不解析响应体。相较旧项目在请求末尾反序列化整份 JSON，此方案不复制可能包含令牌或病史的响应数据。

### 2. 标准库结构化输出与一次异常定位

使用 Python 标准库 `logging` 的集中配置，将 API 请求完成和内部异常事件作为单行 JSON 写到 stdout；字段至少包括 UTC ISO 时间、级别、事件名、`requestId`、方法、路由模板、HTTP 状态、耗时毫秒，并按可用情况写安全的 `channel`、`userId`、`errorCode`。基础级别默认 INFO；若新增可配置级别，必须同步 `.env.template` 和开发说明。已知 4xx 是请求结果而非服务器堆栈；未知 5xx 输出一次独立错误事件加一次请求完成事件，二者共享标识。

为避免 `logger.exception` 自动打印包含 SQL 参数、密码或令牌的原始异常文本，内部错误只记录异常类型以及从 traceback 提取的模块／函数／行号定位信息，不格式化异常对象、不包含局部变量、源码行或请求正文。异常处理器与中间件按同一记录协议标记已记录状态，保证同一异常诊断只出现一次；响应层仍返回固定通用 500。此权衡牺牲部分原始错误消息换取敏感信息保护；必要诊断应通过受控环境另行复现，而不放宽线上日志内容。

### 3. Web 服务器和敏感字段边界

Django 应用日志及 Uvicorn 的应用输出对齐 stdout；关闭或替换 Uvicorn 默认可能输出原始路径／查询字符串的访问日志，避免和应用访问日志重复或泄漏。控制 Django／数据库调试日志级别，应用 formatter 只接收允许的安全字段；不读取 `Authorization`、Cookie、请求／响应正文、手机号、用户名、病史，且不依赖不可信 `X-Forwarded-For`。如果部署以后需要记录来源 IP，应先明确可信代理链和隐私规则，不能直接采信头部。

选择 stdout 而非旧项目的 `TimedRotatingFileHandler`：多进程／多实例下由运行环境负责收集、轮转和权限，应用不要求本地 `logs/` 可写。当前仓库尚无采集器，部署说明必须明确在采集与留存配置完成前仅有进程输出，不承诺持久化。未来推理管理命令出现后可复用日志格式，但其领域事件与保留策略属于那一变更。

## 风险与权衡

- **多个并发请求的用户 ID 或标识串扰** → 每请求作用域并在结束时重置，使用并发不同渠道的 HTTP 测试验证隔离。
- **未预期异常文本及 SQL 诊断泄露敏感内容** → 内部日志只保留安全异常类型与堆栈位置，不记录任意异常消息、局部变量或完整 SQL。
- **Uvicorn、Django 和应用日志重复或出现原始 URL** → 调整访问日志配置并用包含查询密钥的真实 HTTP 请求检查全部进程输出。
- **stdout 无外部采集时日志随进程消失** → 文档明确持久留存依赖部署系统；不创建无验证的进程内轮转方案。
- **统一响应层与日志层各自生成标识** → 日志入口唯一生成，响应只读取；用响应正文、头及完成事件的相等性验收。

## 部署与回退

先启用安全日志配置和请求标识入口，再启用统一回复及用户接口；更新 `docs/development.md` 的启动命令以避免默认访问日志泄漏原始路径，并说明 stdout 的采集责任。上线前验证两并发请求、未知路径、受控 4xx、异常 500 和敏感输入；若回退日志层且统一回复仍在使用，必须同时提供等价 `requestId` 来源，不能返回空或伪造的关联标识。
