# 提案

## 背景

当前服务只有空的 `NinjaExtraAPI` 入口，尚无对外回复和错误契约；用户接口即将接入时若各路由各自封装，客户端会遇到不一致的状态、消息和数据结构。旧项目已有 `code/message/data` 封装与集中异常处理，但部分错误返回 HTTP 200，部分处理器直接输出异常文本，不应原样沿用。

## 变更内容

- 为 `/api/v1/` 下的 JSON 业务接口建立成功与失败共用的回复结构：`code`、`message`、`data`、`requestId`；`code` 拟使用稳定的字符串业务码，成功载荷在 `data` 中，无数据的成功也保留响应体和 `data: null`。实际 HTTP 状态仍与结果一致，不以 HTTP 200 掩盖 401、403、404、405、409、422 或 500。
- 统一处理应用业务错误、Django Ninja 的入参校验与鉴权异常、未匹配的 API 路由／方法及未预期异常。客户端仅接收经过审定的错误码与文案；校验信息不得回显敏感输入，意外异常不得暴露异常文本、堆栈、SQL、路径和配置，即使 API 在调试模式下也如此。
- 让路由声明的响应 Schema 和 OpenAPI 文档反映真实的统一结构，不依赖暗中改写所有响应的中间件；范围仅为 JSON API，不包裹 Django admin、OpenAPI 静态页面或未来的流式／文件响应。
- 将同一 `requestId` 放入回复与响应头，供日志关联；请求标识的生成和日志记录由独立日志能力负责。业务接口只返回领域结果，不各自实现异常包装。

## 能力

### 新增能力

- `api-response`：JSON API 具有一致的成功／失败回复格式、正确的 HTTP 状态、安全的错误文案和可关联请求标识。

### 调整能力

无；现有 `service-bootstrap` 只保证 ASGI 服务可启动，不规定业务回复格式或错误映射。

## 影响

后续实施涉及 `src/config` 的 API 注册及 API 路径的错误兜底、`src/health_service` 的回复 Schema 与业务异常映射，以及正常／异常响应的 HTTP 验证。`user-account-api` 应使用本提案确定的统一契约，`structured-application-logging` 应提供 `requestId` 上下文并可读取结果状态；三份提案分别评审，实施时先对齐共享字段与异常边界。
