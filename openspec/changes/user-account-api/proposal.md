# 提案

## 背景

项目已建立 `User`、`Profile` 及数据库约束，但 `/api/` 尚无注册、鉴权或资料接口，客户端无法使用这些模型。需要先让五个普通渠道安全地共用一个账号和当前健康资料，再接入后续任务等业务能力。

## 变更内容

- 在 `/api/v1/<channel>/` 下，为 `android-cn`、`android-intl`、`ios-cn`、`ios-intl`、`wxapp` 提供用户名密码注册与登录、Access／Refresh Token 刷新轮换及当前 Refresh 登出；这五个渠道共享 `User` 和 `Profile`，令牌绑定登录渠道，跨渠道访问须分别登录。
- 提供本人账号和健康资料读取、资料 `PATCH` 更新；缺席字段不变，可空字段显式 `null` 可清空，结构化病史保留“未填写”与 `false` 的区别。注册时建立账号与空资料；已有账号缺少资料时支持读取及首次补建。
- 限制公开注册可写字段，使用 Django 密码哈希与校验；校验账号可用状态、令牌类型及渠道匹配。旧 Refresh 在轮换或登出后不可再使用；不宣称短期 Access 在登出后立即失效。锁定 JWT 库前验证当前 Django／Ninja Extra 组合的异步鉴权、黑名单和并发刷新行为。
- 用户 API 遵守独立的统一回复与错误契约，并在独立日志能力中记录可关联、已脱敏的请求和异常；不在本变更重复定义响应封装或通用日志框架。
- 不纳入短信及手机号绑定／登录、账号注销、管理端接口、修改用户名、修改或找回密码、任务与文件接口；这些不得因旧项目存在类似路由而被视为已交付。

## 能力

### 新增能力

- `user-auth`：普通渠道共用账号的注册、密码登录、渠道绑定的双 Token 刷新与登出，以及受保护接口的身份校验。
- `user-profile`：仅本人读取和部分更新当前健康资料，保持空值、未知值及结构化病史的语义。

### 调整能力

无；现有 `health-data-model` 规定的是持久化关系，未承诺账号用例或 HTTP 行为。

## 影响

后续实施涉及 `src/health_service` 的应用用例、请求与响应 Schema、API 和鉴权适配，`src/config` 的路由与认证配置，以及密码／令牌／资料接口的行为验证；引入经兼容性验证的 JWT 依赖及必要的黑名单迁移。如新增环境配置，需同步 `.env.template`。新接口依赖 `unified-api-responses` 提供一致响应契约，并与 `structured-application-logging` 对齐 `requestId` 及敏感信息排除规则；三个提案可独立评审，实施时需按共享契约协调。
