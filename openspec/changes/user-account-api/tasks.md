# 任务

## 1. 认证依赖与运行配置

- [ ] 1.1 在隔离验证环境中用当前 Django 5.2、Django Ninja 1.7.1、Ninja Extra 0.31.7 及 Pydantic v2 验证 `django-ninja-jwt` 异步 Bearer 鉴权、签发渠道声明、黑名单迁移及旧 `jti` 行锁能力；以实际 HTTP／PostgreSQL 试验记录结果，若不能满足并发轮换则先修订设计而不锁入不可用依赖。
- [ ] 1.2 固定经验证的 JWT 依赖与 `uv.lock`，配置独立签名密钥、Access／Refresh 有效期及黑名单迁移；同步 `.env.template`，验证 `uv sync --locked`、Django 配置检查及空库和已有业务库的迁移均可运行，缺少必填签名密钥时明确失败。
- [ ] 1.3 在 `docs/development.md` 说明新密钥配置、过期令牌清理及重登要求；核对文档中的配置命令和清理命令能按已安装依赖执行。

## 2. 五渠道注册登录与入口鉴权

- [ ] 2.1 实现普通渠道白名单、公开注册的输入 Schema 及同步事务用例；用 PostgreSQL 集成测试验证密码哈希、账号和空资料同时创建、全局唯一用户名、无效密码与权限字段被拒绝，且 `manager` 无注册入口。
- [ ] 2.2 实现共用的密码登录及渠道声明签发用例；经真实 HTTP 请求验证同一账号在两个渠道登录得到同一用户 ID、不同渠道令牌，并验证不存在的用户名、错误密码及停用账号对外文案一致。
- [ ] 2.3 实现只接受渠道匹配 Access 的本人账号接口，不使用 Session、默认 JWT 登录路由或令牌里的权限快照；用 HTTP 行为测试验证缺失／过期令牌、错用 Refresh、跨渠道 Access 和停用账号均不能取得账号数据。
- [ ] 2.4 更新 `docs/development.md` 的注册、密码登录和 `Authorization: Bearer` 调用示例；实际请求一次并核对返回字段、请求别名与统一回复格式一致。

## 3. Refresh 轮换和登出

- [ ] 3.1 实现按旧 Refresh `jti` 行锁、锁内重检、撤销及重新签发的同步事务流程；用真实 PostgreSQL 并发测试验证同一旧 Refresh 至多成功轮换一次，旧令牌重放、错渠道与停用账号均不能产生新令牌。
- [ ] 3.2 实现只撤销当前 Refresh 的登出流程；用真实 HTTP 请求验证 Access 过期但 Refresh 有效仍能登出、登出后不能刷新、其他独立渠道 Refresh 不受影响，且 Access 仍遵守其剩余有效期。
- [ ] 3.3 在 `docs/development.md` 记录刷新、登出、客户端保存新令牌和旧 Access 自然到期的契约；核对示例请求返回的状态和统一响应字段。

## 4. 本人资料读取与部分更新

- [ ] 4.1 实现本人资料读取与缺失资料的空值投影，不在 GET 中补建；用 PostgreSQL 与 HTTP 测试验证跨渠道共享一份资料、无记录时返回 `gender=0` 和可空值、读取不增加资料行。
- [ ] 4.2 实现资料 PATCH 的字段缺席／显式 `null`、性别未知值和结构化病史键级合并，并对首次补建和 JSON 读改写加事务锁；用数据库与 HTTP 测试验证 `false` 不丢失、已知键删除、未知持久化键被保留、无效测量值不写入及并发更新不互相覆盖。
- [ ] 4.3 限制资料的入参与公开响应字段，拒绝请求指定其他 `userId`；用 HTTP 测试验证不同账号无法读取或改写彼此资料、认证与渠道错误被拒绝，并在 `docs/development.md` 写明 PATCH 和空值示例。
